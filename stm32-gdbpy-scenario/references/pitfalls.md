# Провалы сценариев gdb-py

Пункты собраны по прогонам на STM32F411 (локально и на удалённом стенде) и в Renode. Формат: симптом → причина → правильное действие.

## 1. Запуск GDB

### 1.1 `Python scripting is not supported in this copy of GDB` / `Undefined command`

**Причина:** в xPack и части сборок Arm GNU Toolchain обычный `arm-none-eabi-gdb` собран
без Python; Python-вариант называется `arm-none-eabi-gdb-py3`. Без Python файл сценария
исполняется как команды GDB, и первая же строка (docstring) не команда.

**Правильно:** `python scripts/run_scenario.py --check-gdb`. Скрипт принимает только GDB,
который выполнил `python print(6 * 7)`. В Linux подходит и `gdb-multiarch`.

Python внутри GDB — встроенный интерпретатор той версии, с которой GDB собран
(`python import sys; print(sys.version)`), а не Python хоста. Сторонние пакеты хоста
в нём не видны: сценарий пользуется только стандартной библиотекой.

### 1.2 `TypeError: 'condition' is an invalid keyword argument`

**Было:** `gdb.Breakpoint(symbol, temporary=True, internal=True, condition=cond)`.

**Причина:** в части версий GDB (в том числе 15.2.90 из xPack) конструктор не принимает `condition`.

**Правильно:**

```python
point = gdb.Breakpoint(symbol, temporary=True, internal=True)
point.condition = cond
```

### 1.3 `not in executable format`, `is not a core dump`, `source command requires file name`

**Было (PowerShell):** `Start-Process -FilePath $gdb -ArgumentList @('-nx','-batch',$elf,'-ex',"source $script")`.

**Причина:** `Start-Process -ArgumentList` пересобирает массив в одну строку; `-ex "source x.py"`
разваливается на два аргумента, путь уходит в позиционные как ELF или core. То же с `-iex "set auto-load off"`.

**Правильно:** оператор `&` с массивом (`& $gdb -nx -batch $elf -ex "source tools\x.py"`) или
`subprocess.run([...])` списком в Python, как делает запускатель.

### 1.4 Сценарий молча ничего не проверил

**Причина:** раздел сценария пуст или все проверки внутри условия, которое не выполнилось;
`all([])` в Python — `True`.

**Правильно:** итог PASS только при непустом `checks` (так в шаблоне); каждая ветка
сценария заканчивается проверкой.

## 2. Пробник, стенд и тип МК

### 2.1 Серийник в файле стенда не совпадает с фактическим

**Симптом:** OpenOCD не находит адаптер или, хуже, работает с другой платой того же узла.

**Правильно:** до действий `scripts/environment.py` (локально и на узле) и выбор пользователя;
передавать `--adapter-serial` или `--adapter-usb-location`. Отпечаток изменился — остановиться
и сообщить.

### 2.2 Плата не та

**Симптом:** DEV_ID отличается от профиля (например, `0x469` вместо `0x431`).

**Причина:** на узле несколько пробников, выбран не тот.

**Правильно:** первым шагом сценария читать `DBGMCU_IDCODE` и проверять DEV_ID.

### 2.3 OpenOCD на узле недоступен с хоста

**Причина:** OpenOCD слушает только `127.0.0.1` узла.

**Правильно:** SSH-туннель `-N -L 13333:127.0.0.1:3333` с `ExitOnForwardFailure=yes` и
`ConnectTimeout=10`, затем `--attach 127.0.0.1:13333`.

### 2.4 Команда для узла приходит обрывками

**Симптомы:** `syntax error near unexpected token 'do\r'`, пути вида `D:\dev\null`.

**Причина:** вложенные кавычки и `$` в `ssh host "..."` из PowerShell; `Set-Content` пишет CRLF.

**Правильно:** файл-скрипт с окончаниями LF (`[System.IO.File]::WriteAllText($p, ($s -replace "`r`n", "`n"))`),
`scp`, затем `ssh host "bash /tmp/job.sh"`.

### 2.5 OpenOCD на узле умирает вместе с SSH-сеансом

**Правильно:** `nohup openocd ... > /tmp/ocd.log 2>&1 &` и проверка готовности по журналу.

### 2.6 `nohup: failed to run command '$HOME/...': No such file or directory`

**Причина:** путь с переменной в одинарных кавычках не раскрывается оболочкой узла.

**Правильно:** абсолютный путь или `~/`, `$HOME/`, `${HOME}/` в начале: запускатель и
`environment.py` раскрывают эти формы на узле и до запуска проверяют файл (`command -v`).

### 2.7 Серийник ST-Link нечитаем, пробников несколько

**Симптом:** в списке USB вместо серийника байты или пустота; `adapter serial` не находит пробник.

**Причина:** ST-Link V2 со старой прошивкой отдаёт серийник байтами, а не строкой.

**Правильно:** выбирать по месту USB (`--adapter-usb-location <bus>-<port>` из отчёта
`environment.py`) или обновить прошивку пробника. Место USB меняется при переподключении в
другой порт, поэтому отпечаток сверяется перед каждым прогоном.

## 3. Состояние цели

### 3.1 «Застывшие» значения

**Симптом:** все переменные неизменны, включая счётчик тиков; легко принять за «сигнала нет».

**Причина:** цель осталась в halt после прошлого прогона: `detach` при остановленном ядре.

**Правильно:** перед действием убедиться, что тики растут; в конце сценария на плате —
`continue &`, затем `detach`.

### 3.2 Проверка «ядро работает» провалилась сразу после подключения

**Причина:** `target remote` останавливает цель; два чтения счётчика через GDB видят одно значение.

**Правильно:** `core_running(&uwTick)` из шаблона: окно работы (`monitor resume`), чтения по SWD
(`mdw`/`memU32`), затем `monitor halt`.

### 3.3 `Cannot execute this command while the target is running`

**Причина:** чтение через GDB (`parse_and_eval`, `read`) при работающем ядре. Частый путь —
`monitor resume` без парного `monitor halt`: сервер отпустил ядро, а GDB считает цель
остановленной; затем `interrupt` или чтение ломаются.

**Правильно:** на ходу читать только `read_running()` внутри `running_window()`; чтения GDB —
после выхода из окна. Цель для долгой работы отпускать в конце сценария `continue &`.

### 3.4 HardFault вместо сценария

**Симптом:** кадр `HardFault_Handler`, `Could not read register 'pc'`, `reach` висит.

**Причина:** продолжение испорченного контекста после прошлого прогона.

**Правильно:** `reset run` через OpenOCD, затем проверить тики. Сброс стирает данные и
заглушки в SRAM (например, буфер RTT): если там что-то работает, снять это штатно до сброса.

### 3.5 Воздействие игнорируется

**Причина:** обработчик принимает событие только в определённом состоянии автомата.

**Правильно:** до действия дождаться и проверить нужное состояние.

## 4. Ожидание результата

### 4.1 `continue` без точки останова

GDB не возвращается: цель работает, остановки не будет. Ставить точку перед каждым `continue`.

### 4.2 Условие, которое не наступит

`reach` с условием висит бесконечно, если состояние не наступит (HardFault, выключенный
тракт). Ограничение — `--timeout` запускателя; итог TIMEOUT с последним шагом `STEP`.

### 4.3 Ожидание по часам хоста

Остановки отладчика растягивают исполнение цели, а часы хоста идут. Ждать по тикам прошивки.

### 4.4 Эмулятор останавливается раньше сценария

Прошивка, завершающая себя семихостингом (`SYS_EXIT`), останавливает ядро в Renode:
`reach` возвращается с чужим кадром и даёт FAIL. Сценарий должен укладываться в время
работы такой сборки или использовать сборку без самозавершения.

### 4.5 Renode: GDB-сервер запущен, а порт недоступен

В части песочниц и контейнеров нет IPv6 на loopback, и сервер Renode недоступен. Тогда
сценарий выполняется на другой машине, а для чтения памяти без GDB подходит монитор Renode.

## 5. Результат и уборка

### 5.1 Проверка управляющего сигнала вместо результата

Сценарий PASS, а эффекта нет: проверялось «записали» или «ключ включён». Проверять
наблюдаемое следствие и соседние признаки (SKILL.md, раздел 6).

### 5.2 Записанное не возвращено

Исключение после `write` оставило изменённую переменную. В шаблоне `restore()` выполняется
в `finally` и проверяется чтением; неподтверждённое восстановление даёт ERROR.

### 5.3 Забытые процессы и туннели

Следующий прогон: порт занят, пробник занят. Запускатель убирает только свои процессы.
Ручные туннели — по сохранённому pid; OpenOCD на узле — `pkill -f '[o]penocd'`, если он ваш.
Освобождение порта проверять реальным подключением.
