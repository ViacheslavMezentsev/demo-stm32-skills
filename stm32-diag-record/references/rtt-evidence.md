# Доказательства записи RTT и начальные интервалы

## Что сохраняется

В mcap и bag два служебных канала `std_msgs/UInt32`:

- `/_diag/rtt/seq`: исходный uint16 из заголовка RTT, без перенумерации, переход 65535 → 0 сохраняется.
- `/_diag/rtt/tick_ms`: исходный uint32 из того же заголовка. Дубликаты и переполнение сохраняются.

Оба сообщения получают время `tick * 1 000 000` наносекунд, как поля кадра. При одинаковом tick
сопоставляйте сообщения по порядку внутри каждого канала; группировать только по уникальному времени
нельзя. MCAP `sequence` — отдельный счётчик писателя, для анализа потерь используйте payload канала seq.
При переполнении tick время контейнера тоже возвращается к нулю: читатель, сортирующий по времени,
переставит кадры; в MCAP читайте порядок записи (`iter_messages(log_time_order=False)`).

Файл `<имя>.rtt.json` относится к записи, указанной в `record`. `schema: 1`:

| Поле | Значение |
| --- | --- |
| `stop_reason` | `duration`, `interrupt`, `eof` или `error`; EOF — закрытие потока, не доказательство полной длительности |
| `record_closed` | писатель успешно закрыл файл; это не проверка восстановления регистров цели |
| `elapsed_host_seconds` | время на хосте от начала настройки RTT до выхода из чтения; не длительность по tick |
| `timer`, `frame`, `buffer_bytes`, `rtt_poll_ms` | параметры данного запуска |
| `stats.frames` | принятые парсером кадры |
| `stats.written`, `metadata_written` | записанные сообщения полей и служебных каналов, отдельно |
| `stats.out_of_range` | отброшенные значения полей; seq/tick таких кадров остаются |
| `stats.first_seq`, `last_seq`, `first_tick`, `last_tick` | границы принятого потока; `null` без кадров |
| `stats.seq_gaps`, `dropped_est` | число разрывов и сумма `(seq - предыдущий_seq - 1) & 0xFFFF` |
| `stats.resyncs`, `bad_tail` | события поиска новой границы; число оставшихся в парсере байтов при завершении |
| `stats.tick_repeats`, `tick_wraps`, `tick_backwards`, `max_tick_step_ms` | одинаковые метки, переходы через ноль, обратные скачки и максимальный прямой шаг |
| `target_dropped` | `null`: счётчик dropped из SRAM цели не считывался |

Оценка по seq охватывает **только промежутки между принятыми кадрами**. Она не видит потерянный префикс,
непрочитанный хвост кольца, целые обороты 65536 номеров и пропущенные аппаратные события таймера,
не вызвавшие ISR. При нарушении порядка/дублировании seq формула тоже даёт большой разрыв — это оценка,
не точное число потерь цели. Прямой шаг tick определяется по модулю 2^32; шаг не меньше 2^31 считается
обратным скачком (для таких длинных перерывов вывод неоднозначен). CRC в RTT-кадре нет.

JSON записывается через временный файл и замену при нормальном завершении, Ctrl+C или исключении Python
в чтении. Убийство процесса, отключение питания хоста или ошибка диска могут помешать сохранению.
Сначала сохраняется статистика потока. После завершения GDB в JSON добавляется `teardown`;
для подтверждения восстановления нужны `teardown.ok: true` и продвижение tick, а не только `record_closed`.

## Почему в начале встречаются одинаковые tick и короткий период

`install()` останавливает ядро, загружает образ и включает таймер ещё перед `resume`. Счётчик времени
прошивки растёт в SysTick ISR, который во время остановки не выполняется. Периферийные таймеры могут
продолжать считать в debug halt, если их не заморозили средствами DBGMCU. При возобновлении возможны
накопленные pending-прерывания и сдвиг фаз относительно программного tick.

В прошивках с CMSIS `SysTick_Config` SysTick обычно получает самый низкий приоритет. Заглушка приоритет
свободного IRQ не задаёт, поэтому он зависит от исходного состояния NVIC. Если её IRQ выше SysTick,
несколько выборок могут увидеть старый tick. Вложенное прерывание также означает, что поля кадра — не
атомарный снимок всей структуры.

Как различать случаи:

1. Сравнить исходный seq двух кадров с одинаковым tick и значения остальных полей. Разные значения
   исключают простое побайтное дублирование кадра; последовательные seq подтверждают разные вызовы ISR.
2. Найти первый переход рабочего счётчика таймера и следующий. Первый мог быть обработкой накопленного
   pending, поэтому интервал до следующего события меньше штатного. Затем проверить установившийся период.
3. Не вычислять длительность halt только как разность штатного и первого периода: неизвестны исходная
   фаза, pending, заморозка таймеров и порядок обслуживания IRQ.
4. Для подтверждения на железе снять перед установкой `DBGMCU_APB1_FZ`, TIMx CNT/SR, NVIC pending/priority
   и сопоставить события с внешним анализатором или счётчиком, который не зависит от SysTick ISR.
   Повторить с теми же ELF/полями и сохранить консольный отчёт вместе с mcap/bag и JSON.

Это механизм, согласующийся со стартовыми переходными процессами, а не доказательство причины каждого
конкретного интервала. Ради гладкого графика не удаляйте первые кадры и не подменяйте их tick временем хоста.

## GDB-завершение (1.7.0)

Для записи нужен GDB с Python из тулчейна (`--cleanup-gdb` задаёт другой). OpenOCD запускается самим
рекордером, telnet и GDB слушают разные свободные порты loopback; по умолчанию GDB — 3334.
Внешний `--use-running` не поддержан для записи rtt-timer, чтобы не завершать чужую GDB-сессию.
Перед изменением цели проверяются GDB, отсутствие enabled/pending/active IRQ выбранного таймера,
выключенное тактирование таймера и продвижение tick. Доктор дополнительно читает IABR.

Порядок завершения:

1. GDB подключается без загрузки ELF/прошивки и без сброса, останавливает ядро.
2. Выключает CEN/UIE, очищает SR, отключает IRQ и очищает pending. Каждая существенная запись проверяется чтением.
3. Пока IABR выбранного IRQ установлен, выполняет `stepi` только при PC внутри нашей заглушки
   (от `stub` до `params`). Максимум 512 инструкций; весь GDB-процесс ограничен 90 секундами.
   Так выполняются настоящие `pop`/`bx lr`, без GDB `return` или подмены PC/SP/LR.
4. После выхода из IRQ проверяет отсутствие pending/enabled, возвращает VTOR и только свой бит RCC.
   Изменившиеся за время записи биты другой периферии сохраняются.
5. `detach` возобновляет цель. Хост читает tick дважды с паузой 250 мс, IABR/ISER/ISPR, VTOR и DHCSR.
   Успех требует продвижения tick, отсутствия IRQ таймера и остановки ядра.

`<имя>.teardown.json` и поле `teardown` в `<имя>.rtt.json` содержат `ok`, `stage`,
`registers_restored`, число шагов, результаты readback и проверки после resume. При ошибке — `error`.
Журнал GDB — `<имя>.gdb.log`; входные параметры — `<имя>.cleanup.json`.
`registers_restored: true` без `ok: true` означает, что продолжение работы не подтверждено.

При активном Default_Handler или неизвестном вложенном ISR алгоритм отказывает и не возвращает VTOR.
При тайм-ауте/сбое связи результат тоже считается отказом; рекордер пытается остановить ядро для диагностики.
Автоматического сброса, исправления стека и принудительного выхода из исключения нет. Повторный Ctrl+C
во время завершения игнорируется до окончания ограниченной по времени проверки. Завершение процесса
из диспетчера задач этот протокол обходит.

Проверка роста tick — проверка выбранного счётчика, не доказательство исправности всей прошивки.
Счётчик должен регулярно меняться; прошивка, которая намеренно останавливает tick, получит отказ.
После успешного прогона отдельно проверяют прикладную логику и повторяют тест с Ctrl+C.
Синтетические тесты не подтверждают поведение реального GDB/ST-Link; аппаратная приёмка обязательна.
