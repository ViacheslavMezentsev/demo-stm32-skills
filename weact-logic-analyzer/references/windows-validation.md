# Аппаратная проверка Windows, 2026-10-19

WeAct LogicAnalyzerV1 (идентификация модели владельцем), восемь каналов, USB-хаб;
BlackPill F411CE, общая земля, D0 → PC13. Прошивка stm32-hwtest-blackpill переключает
LED после ожидания 500 тиков и обработки цикла. HSI ранее измерен около 973 tick/с.
Серийные номера, персональные пути и сырые аппаратные журналы в Git не сохраняются.

На двух клонах ранее также наблюдался обрыв старой сборки; смена кабеля и подключение напрямую
его не устранили. На старой сборке сырой binary на накопитель проекта записал все 500000 байт.
Это локализует зависимость от версии/формата/пути. Точная причина задержек файловой системы
и конкретное исправление новой версии не установлены. Старый srzip открывает/закрывает архив
на каждый блок; это возможный механизм задержек, а не доказательство дефекта накопителя.
При использовании старой сборки проверенный обход — TEMP → проверка → копирование.

Полная запись nightly на накопителе проекта: период 1,0287575 с (4 полных периода),
высокий уровень 514,380 мс, низкий 514,390 мс. Это согласуется с HSI и ожиданием 500 тиков;
абсолютная точность часов анализатора не калибрована.

Высокие частоты проверялись на медленном PC13: это проверка доставки объёма данных, не полоса
пропускания входов, точность коротких импульсов или отсутствие всех возможных потерь.
Предыстория rising требует отдельного исследования; до него использовать pretrigger=0.
В сообщении sigrok при триггере число может учитывать только данные после триггера:
200000 в файле при сообщении 180000 само по себе не означает обрыв.

## Обязательная приёмка автоматизации

`LogicAnalyzer.collect()` сравнивает фактические число отсчётов и samplerate с запросом,
выдаёт LAError при несовпадении даже с rc=0 и оставляет файл для расследования.
Предупреждения не скрываются. Повреждённый архив — ошибка; ожидание без события ограничено
таймаутом. На Windows прекращение ожидания завершает процесс, файл может быть незавершённым
и не считается успешной записью. Проверять возможность следующего открытия анализатора.

Открыто: точный механизм аномалии на USB-тракте с хабом, UART BluePill, точные тестовые импульсы,
повтор матрицы на Ubuntu 20.04 ARM64 через SSH, инфографика по итогам серии.

## Программные проверки

Девять регрессий без оборудования: полный файл, неполный файл с rc=0 (с предупреждением
и без), полный файл с посттриггерным предупреждением, избыток отсчётов, неправильная частота,
повреждённый архив, отсутствующий файл, ненулевой код, неверный запрос samples.
Kits также проверяет синтетические UART/I2C/SPI и demo-драйвер. Старый тест demo с триггером
принимал 4096 вместо 5000 отсчётов; теперь ожидается отклонение неполного захвата.

## Прямое USB-подключение: контроль после хаба

На той же nightly и WeAct после исключения хаба:

- 24 МГц × 1,2 с: оба файла, в каталоге проекта и в TEMP, содержат ровно 28800000
  отсчётов. CRC архива на накопителе проекта проверен; PC13 имеет ожидаемые фронты.
- Rising, 100 кГц × 2 с: шесть записей с 10% предыстории, две с 50%, две без предыстории.
  Во всех 200000 отсчётов; лишних переходов не обнаружено. Полные импульсы в серии
  примерно 514–515 мс. Это ограниченная серия, не гарантия для любого стенда.
- В двух новых записях с предысторией экспорт через sigrok в binary побайтно совпал
  с данными Python-обёртки. Старый аномальный файл также совпал при независимом экспорте:
  короткие импульсы действительно сохранены в файле, а не добавлены анализом Python.
- Триггер может находиться раньше заданных 10%/50%, если событие пришло до накопления
  всей предыстории. Например, 0,09369 с вместо 0,2 с при корректных следующих полупериодах.
  Это не считать лишним фронтом; положение события нужно находить по сигналу.
- При первом сканировании после переподключения FX2 загружает прошивку и переобнаруживается.
  Следующая немедленная команда может получить No devices found; дождаться повторного scan
  с доступным устройством перед записью, не смешивать это с потерями во время захвата.

Прямое подключение устранило наблюдавшиеся отказы в этой серии. Ранее успешные 16 МГц
через хаб не гарантируют 24 МГц.

## Обратный опыт через тот же хаб

Владелец вернул WeAct на прежний хаб без изменения щупов и прошивки MCU. При этом:

- 24 МГц × 1,2 с: только 530944 отсчёта; журнал содержит таймауты USB и отмену передачи.
- Rising с 10% предыстории: в первой из трёх записей снова лишние переходы, полные импульсы
  от 0,24 до 15,4 мс среди ожидаемых примерно 514 мс. При этом файл содержит все 200000
  отсчётов и 209 передач в подробном журнале помечены COMPLETED, без USB-ошибок.
  Два следующих запуска чистые: дефект не возникает при каждом захвате.
- Контроль без предыстории чистый; дополнительный захват без триггера также чистый.

Таким образом, наблюдаемая проблема воспроизводимо связана с этим USB-трактом через хаб,
а не только с форматом файла, местом сохранения или Python-разбором. Это не доказывает дефект
всех хабов и не позволяет без дальнейших измерений разделить электрическую причину,
контроллер хаба, драйвер Windows/libusb и обработку предыстории. Утверждать, что короткие
импульсы реально генерирует MCU, также нельзя. Рабочий маршрут данной серии — прямое USB.
Для непроверенного тракта сохранять pretrigger=0 и контролировать форму сигнала по эталону;
полнота файла, CRC ZIP и rc=0 не обнаруживают такую аномалию сами по себе.
