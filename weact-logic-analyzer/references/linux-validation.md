# Аппаратная проверка Ubuntu ARM64, 2026-10-19

OrangePi 5, Ubuntu 20.04.6 LTS aarch64, Python 3.8.10, запуск по SSH.
WeAct LogicAnalyzerV1, восемь каналов; BlackPill F411CE, общая земля, D0 → PC13.
Использована неизменённая обёртка версии 1.2.0. Прошивка MCU не изменялась.
Сырые записи и журналы сохранены отдельно от Git.

## Окружение

sigrok-cli 0.7.1, libsigrok runtime 0.5.2 (сборка против 0.5.1),
libsigrokdecode runtime 0.5.3, libusb 1.0.23. Doctor подтвердил доступ к USB,
прошивку fx2lafw и права plugdev. При нескольких анализаторах выбран конкретный
conn из повторного scan; адрес меняется после переподключения.
Проверенная Windows nightly не является минимальным требованием для Linux.

Базовая запись: средний период 1,02784 с по четырём полным периодам
(1,02771–1,02794 с); высокий уровень 513,890 мс по четырём импульсам,
низкий 513,952 мс по пяти. Частота около 0,973 Гц согласуется с предыдущими
наблюдениями HSI этой платы. Абсолютная точность часов анализатора не калибрована.

Во всех десяти обычных захватах проверены число отсчётов и samplerate;
полные импульсы D0 укладываются в контрольное окно 500–530 мс.
Обрезанные границами записи импульсы исключены. Высокие частоты на медленном PC13
проверяют доставку данных, а не полосу входа или точность декодирования протокола.
Это короткая серия на одном тракте, не предельный тест всех USB-конфигураций.

Предыстория может не успеть накопиться: при pre=50% первый переход оказался на
0,16085 с, а не на 1 с. Сообщение sigrok «Device only sent» при триггере может
учитывать только посттриггерные отсчёты: полный файл принят по фактической длине.
Результаты не устанавливают причину аномалии Windows через прежний хаб.

## CAN, 30.10.2026 (версия 1.3.0, тот же узел, DroneCAN 1 Мбит/с)

Шина из двух узлов, анализатор на выходе приёмника трансивера узла (D1) и на передатчике его
контроллера (D0). `can` на D1: 1108 кадров за 12 с, все без замечаний и с доминантным ACK, счёт по ID
совпал с независимым побитовым декодером; `can-role`: D0 — TX узла (подтверждения у 1084 из 1084 чужих
кадров, свои 24 кадра есть на линии), в обратную сторону — «каналы перепутаны». При параллельных
candump, клиенте CAN и чтении UART 8 МГц × 12 с дважды записались ~3 с (`Device only sent`, код 0); без
нагрузки `capture` 8 МГц × 12 с и 4 МГц × 12 с — полные.
