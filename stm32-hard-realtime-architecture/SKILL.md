# Архитектурные паттерны: STM32 Hard Real-Time

Этот навык описывает стандарты и паттерны проектирования для малых встраиваемых систем (ПЛК, контроллеры БПЛА, умные датчики). Применение этих паттернов гарантирует предсказуемость, отсутствие утечек памяти, защиту от аппаратных сбоев и легкость стендового тестирования.

## 🧱 1. Архитектура «Синхронный Супер-цикл» (Time-Triggered Super-loop)
**Проблема:** Обработка прерываний (ISR) и сетевых пакетов нарушает предсказуемость выполнения критической бизнес-логики.
**Паттерн:** Разделение `loop()` на две строгие фазы.
*   **Асинхронная фаза:** Выполняется в каждом такте (опрос сети, сброс Watchdog, поллинг UART).
*   **Синхронная фаза:** Выполняется строго по таймеру (например, `if (now - lastMs >= 1)`). Включает чтение датчиков, математику, шаг FSM и обновление выходов.

```cpp
void loop() {
    IWatchdog.reload();
    networkManager.poll(); // Асинхронно

    static uint32_t lastLogicMs = 0;
    if (millis() - lastLogicMs >= 1) {
        lastLogicMs = millis();
        // Строго синхронно (1 кГц)
        sensors.update();
        fsm.update();
        hmi.update(fsm.getState());
    }
}
```

## 🧱 2. Внедрение зависимостей без кучи (Zero-Cost Dependency Injection)
**Проблема:** Тесная связность модулей (spaghetti-code), когда сетевой класс `ModbusManager` напрямую вызывает методы `FsmManager`.
**Паттерн:** Использование `etl::delegate` вместо указателей на классы или `std::function` (которая использует кучу). Модуль связи ничего не знает о бизнес-логике, он просто "дергает" делегаты.

```cpp
class ModbusManager {
    etl::delegate<void(bool)> onValveCmd;
public:
    ModbusManager(etl::delegate<void(bool)> valveCb) : onValveCmd(valveCb) {}
    
    void parsePacket(uint8_t* data) {
        if (data[0] == CMD_OPEN_VALVE) onValveCmd(true);
    }
};

// В main.cpp связываем их:
auto valveCb = etl::delegate<void(bool)>::create<FsmManager, &FsmManager::cmdValve>(fsm);
modbus.init(valveCb);
```

## 🧱 3. Полиморфизм "Черного ящика" (In-Place Factory)
**Проблема:** Необходимо поддерживать разные аппаратные модификации устройств (ШИМ-насос, релейный насос, шаговый двигатель), но динамическая память (`new`) запрещена.
**Паттерн:** Базовый класс `IActuator`. Фабрика читает параметр EEPROM `sys.hw_type` и конструирует нужный драйвер в статическом буфере с помощью `placement new`.

```cpp
alignas(8) uint8_t driverMemory[128];
IActuator* activeDriver = nullptr;

void init(const char* type) {
    if (strcmp(type, "PWM_PUMP") == 0) {
        activeDriver = new (driverMemory) PwmPumpDriver();
    } else {
        activeDriver = new (driverMemory) RelayPumpDriver();
    }
}
```

## 🧱 4. Программная симуляция с изоляцией выходов (SIL)
**Проблема:** Интеграционное тестирование верхнего уровня (ROS/SCADA) требует проверки всей цепочки обмена данными, но физическое срабатывание механизмов "на столе" опасно.
**Паттерн:** Внедрение флага `sys.sim_mode`. При его активации драйверы **аппаратно глушат выходы** (0 В / Hi-Z), но начинают генерировать идеальную "виртуальную" телеметрию, обманывая FSM.

```cpp
void ValveDriver::update() {
    if (isSimulated) {
        digitalWrite(PIN_VALVE_OUT, LOW); // Аппаратная блокировка!
        virtual_telemetry_state = expected_cmd; // Виртуальный ответ
        return;
    }
    // Реальная работа с железом...
}
```

## 🧱 5. Аппаратная самодиагностика (BIST) и Замкнутый контур
**Проблема:** Слепая выдача управляющего сигнала (например, `RELAY_ON`) может привести к аварии, если исполнительный механизм не подключен или оборван.
**Паттерн:** Перед переходом в активное состояние, драйвер производит "прозвонку" цепей. Выдача боевых сигналов блокируется до получения валидного аппаратного ответа (Замкнутый контур).

```cpp
void startMotor() {
    // 1. Проверяем целостность цепи термистора двигателя (BIST)
    if (analogRead(PIN_TEMP) > THRESHOLD_OPEN_CIRCUIT) {
        changeState(FAULT); return;
    }
    // 2. Подаем слабый тестовый сигнал, ждем ответа
    // 3. Только после получения Ready подаем силовое питание
}
```

## 🧱 6. Блокировка параметров (In-flight Parameter Lock)
**Проблема:** Оператор (или скрипт) пытается изменить калибровочные коэффициенты или стереть EEPROM в момент, когда станок выполняет критическую операцию.
**Паттерн:** Обработчик протокола сверяется со статусом `FSM`. В активных состояниях любые команды на запись или сохранение молча отклоняются.

```cpp
void onConfigPacketReceived() {
    if (fsm.getState() == State::MOTOR_RUNNING || fsm.getState() == State::CUTTING) {
        sys_log("Config write BLOCKED! System is in ACTIVE mode.");
        return; // Игнорируем
    }
    registry.updateParam();
}
```

## 🧱 7. Отказоустойчивость (Graceful Degradation)
**Проблема:** Падение напряжения (Brown-out), потеря I2C-датчика или обрыв кабеля вызывают `HardFault` или зависание в `while(1)`, лишая оператора телеметрии.
**Паттерн:** Постоянный мониторинг здоровья (Health Monitor). При критическом сбое FSM аппаратно обесточивает исполнительные механизмы, переходит в состояние `HARDWARE_FAULT` и **продолжает транслировать статус по сети**.

```cpp
if (measureVdd() < 3000) { // Просадка ниже 3.0 В
    actuator.emergencyStop();
    fsm.setHardwareFault(true);
    // Сеть продолжает работать, SCADA видит код ошибки.
}
```

## 🧱 8. Режим Конфигурационной тишины (Network Muting)
**Проблема:** Передача объемных конфигурационных параметров по шине (CAN/RS-485) совпадает с высокочастотной телеметрией, переполняя буферы и вызывая потерю пакетов.
**Паттерн:** При получении запроса на чтение/запись параметра, коммуникационный менеджер заводит таймер (например, 100 мс), на время которого "глушит" всю несрочную телеметрию, отдавая приоритет конфигурационному пакету.

```cpp
if (configMuteTimeoutMs > 0) {
    // Не шлем телеметрию датчиков, очищаем шину для ответа с параметрами
} else {
    sendSensorData();
}
```
