### 1.6. Соглашения документа

1.6.1. Модальность: **ДОЛЖНА / ДОЛЖЕН** — обязательное требование; **СЛЕДУЕТ** — рекомендуемое; **МОЖЕТ** — допустимое.

1.6.2. Нумерация: каждый пункт имеет номер вида `X.Y.Z`. Номер требования не переиспользуется и не сдвигается; исключённое требование остаётся в тексте с пометкой «(исключено)». Тест-кейсы нумеруются `TC-NN`, вопросы — в пространстве подраздела 9.2, приложения — латинскими буквами.

1.6.3. Маркеры происхождения в конце требований:

| Маркер | Значение |
| :---: | :--- |
| **[R]** | Восстановлено из существующего кода, поведение сохраняется. |
| **[N]** | Новое требование. |
| **[U]** | Уточнение или исправление относительно существующего кода: поведение улучшено или зафиксировано явно. |

1.6.4. Разделы 1–2 и приложения — информативные; разделы 3–7 — нормативные.

1.6.5. Ссылки на пункты ТЗ из кода оформляются по приложению B.

1.6.6. Правила ведения документа:

- ревизия имеет номер `M.m` и статус («черновик для согласования», «на согласовании», «утверждено»); минорная часть растёт с каждым циклом согласования, мажорная — при утверждении или смене архитектуры;
- каждая ревизия добавляет строку в историю ревизий и, начиная с 1.1, блок «Изменения ревизии X.Y» (новейший сверху) с таблицей изменённых пунктов;
- новые и изменённые пункты ревизии помечаются в конце `(р.X.Y)`;
- ревизия обновляет всё, на что влияет: вопросы (раздел 9), тест-кейсы (раздел 7), матрицу (раздел 8), приложения;
- решённые вопросы не удаляются: меняются статус, решение и ссылки на пункты, где решение записано нормативно.

## Приложение B. Соглашение о ссылках на ТЗ из кода

B.1. Ссылка на требование оформляется однострочным комментарием рядом с реализацией: `// ТЗ 4.1.2`. Для нескольких требований — перечисление через запятую: `// ТЗ 4.2.1, 4.2.2`.

B.2. Для тестов используется идентификатор тест-кейса и номера проверяемых требований, например: `// TC-01: ТЗ 4.1.1, 4.1.2`.

B.3. Пример:

```cpp
// ТЗ 4.1.1: повторная инициализация запрещена.
if ( initialized_ ) return false;
```

B.4. При удалении требования из документа его номер сохраняется с пометкой «(исключено)» (п. 1.6.2); комментарий в коде удаляется вместе с реализацией.
