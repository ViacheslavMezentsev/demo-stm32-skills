## 1. Введение

### 1.1. Назначение документа

1.1.1. Документ определяет требования к подсистеме хранения, валидации и доступа к конфигурационным параметрам встраиваемого устройства на STM32 с постоянным хранением значений во Flash-памяти, эмулирующей EEPROM.

1.1.2. Документ является основой для реализации и верификации кода: каждое требование имеет уникальный номер, на который ссылаются комментарии в коде, тесты и матрица прослеживаемости (раздел 12).

### 1.2. Область применения

1.2.1. Требования применимы к модулю `ParamRegistry` и связанным с ним файлам таблицы параметров и формата хранения.

1.2.2. Документ не описывает пользовательские интерфейсы конфигурации (CLI, DroneCAN) и низкоуровневый драйвер Flash. Требования к их взаимодействию с подсистемой приведены в разделе 8.

### 1.3. Метод формирования

1.3.1. Требования восстановлены из поведения существующего кода (формат хранения v1: позиционная адресация слотов, магия `PARM`).

1.3.2. Там, где код v1 не содержит явного решения или содержит дефект, зафиксировано поведение целевой реализации v2 (формат KVS, магия `PAR2`, CRC32) с соответствующим маркером происхождения (п. 1.6.3).

1.3.3. Целевой реализацией считается реализация плана перехода на KVS (редакция 2). В случае расхождения между этим документом и кодом расхождение считается дефектом одного из них и разрешается пересмотром ревизии документа. Известные расхождения ревизии 1.1 перечислены в приложении F. `(р.1.1)`

1.3.4. Ревизия 1.1 дополнительно опирается на журнал загрузки прошивки v0.3.0 (приложение E) и ответы заказчика на открытые вопросы ревизии 1.0 (раздел 13). `(р.1.1)` Ревизия 1.2 опирается на исходный код контроля целостности прошивки, фрагмент `PayloadDriver::init()` и ответы заказчика на вопросы ревизии 1.1. `(р.1.2)`

### 1.4. Термины и сокращения

| Термин | Определение |
| :--- | :--- |
| Параметр | Именованная конфигурационная величина устройства: имя, тип, значение, заводское значение, допустимая область, флаги. |
| Таблица | Массив заводских описаний параметров в ROM (`defaultParamsList`). |
| Реестр | Экземпляр `ParamRegistry`, содержащий рабочие значения в RAM. |
| Persistent (R/W) | Параметр, изменяемый через `setValue` и сохраняемый в хранилище. |

## 2. Общее описание

### 2.1. Контекст

2.1.1. Подсистема работает в составе встраиваемого устройства на STM32G474 с интерфейсами конфигурации (командная строка и DroneCAN GetSet). Интерфейсы читают и изменяют параметры по индексу и имени, а также инициируют сохранение и сброс к заводским значениям.

2.1.2. Подсистема отвечает за: хранение описаний параметров, рабочие значения в RAM, проверку допустимости значений, сохранение в энергонезависимую память и восстановление при старте.

2.1.3. Конфигурирование параметров, как правило, выполняется на этапе старта платы: внешнее приложение по DroneCAN v0 (или оператор через встроенный отладочный CLI) устанавливает значения и подаёт команду сохранения; целостность конфигурации проверяет внешнее приложение. Параметры, кроме `sys.hw_ver` и `sys.board_type`, допускают изменение в процессе работы системы и применяются без перезагрузки (п. 3.3.5). `[R]` `(р.1.2)`

2.1.4. Тип платы (`sys.board_type`) жёстко связан с типом нагрузки. Значение по умолчанию `lts-5l-generic` — «безопасный» тип: он отключает код, зависящий от типа нагрузки. После перезагрузки по типу платы выполняются начальные настройки и создаются экземпляры нужных классов. `[R]` `(р.1.1)`

2.1.5. Перезагрузка платы выполняется только по командам (команды сохранения по CAN и в CLI). Подсистема параметров перезагрузку не инициирует, а только выставляет флаг необходимости перезагрузки (п. 5.6). `[R]` `(р.1.1)`

### 2.4. Границы

2.4.1. Вне области ТЗ: реализация CLI и DroneCAN, драйвер Flash, отказоустойчивая запись в две страницы (решение заказчика — п. 9.3.3).

2.4.2. Специальные режимы обмена по DroneCAN — Combat (запрет записи со стороны прошивки) и mute (временная пауза передачи в режиме конфигурации) — являются частной реализацией CAN-слоя и в архитектуру системы параметров не входят. При запрете записи ответ `GetSet` содержит неизменённое значение (п. 8.7.6), а ответ `ExecuteOpcode` — `ok = false`. Режим mute применять не рекомендуется. `(р.1.6)`

2.5.2. Динамическая память (куча) не используется.

2.5.3. Используются контейнеры ETL (`etl::variant`, `etl::string`) и, при программной реализации CRC, собственная функция пословного расчёта либо `etl::crc32_mpeg2` (п. 8.6.2). `(р.1.2)`

2.5.4. Среда исполнения использует newlib-nano: спецификаторы `%lld` и `%f` в `printf`-подобных функциях недоступны.

2.5.5. Версии инструментов по журналу загрузки: GCC 14.2.1, Arduino Core STM32 v2.12.0, STM32Cube HAL v1.2.5, ETL 20.47.1. Профиль ETL: исключения отключены, RTTI отключён. Следствие: обращение к неактивной альтернативе `etl::variant` не приводит к исключению и недопустимо (п. 5.3.5). `[R]` `(р.1.1)`

## 3. Модель параметра

### 3.1. Типы значений

3.1.1. Подсистема ДОЛЖНА поддерживать четыре типа значений: знаковое целое 64 бит (INT), вещественное одинарной точности (FLOAT), логическое (BOOL), строка (STRING). `[R]`

3.1.2. Тип параметра ДОЛЖЕН определяться при описании в таблице и НЕ ДОЛЖЕН изменяться во время работы. `[R]`

3.1.3. Рабочее значение ДОЛЖНО храниться в RAM в типобезопасном контейнере (`ParamValue`, `etl::variant`) без динамического выделения памяти. `[R]`

3.1.4. Строковое значение в RAM ДОЛЖНО иметь ёмкость не менее 31 символа (`PARAM_STRING_MAX_LEN`). `[R]`

3.1.5. Строка persistent-параметра ДОЛЖНА быть не длиннее 27 символов (`PARAM_STRING_STORED_MAX_LEN`), так как слот хранилища имеет фиксированный размер 32 байта. `[N]`

3.1.6. Длины строк измеряются в байтах (кодировка UTF-8): слово «символ» в п. 3.1.4, 3.1.5, 3.5.3 означает байт. `[U]` `(р.1.2)`

3.1.7. RO-строки МОГУТ содержать многобайтные символы UTF-8 (например, русскоязычное название нагрузки, где кириллический символ занимает 2 байта); имена параметров и допустимые значения persistent-строк — ASCII. `[R]` `(р.1.2)`

### 3.2. Атрибуты параметра

3.2.1. Каждый параметр ДОЛЖЕН иметь: имя, тип, рабочее значение, заводское значение, допустимую область (минимум и максимум; для строк — допустимое множество при наличии), флаги. `[R]` `(р.1.1)`

3.2.2. Имя ДОЛЖНО быть непустой ASCII-строкой, уникальной в пределах таблицы. `[R]`

3.2.3. Для BOOL пределы ДОЛЖНЫ быть фиксированы значениями `false` и `true`; для STRING числовые пределы не используются. `[R]`

3.2.4. Для RO-параметров числовых типов и BOOL минимум и максимум ДОЛЖНЫ совпадать с заводским значением. `[R]`

### 3.3. Классы поведения и флаги

3.3.1. Параметр ДОЛЖЕН относиться ровно к одному из классов, определяемых флагами `READONLY` и `RAM_ONLY`:

| Класс | Флаги | Значение в RAM | `setValue` | Сохраняется в EEPROM | Значение при старте |
| :--- | :--- | :---: | :---: | :---: | :--- |
| R/W (persistent) | нет `READONLY`, нет `RAM_ONLY` | да | да | да | Из EEPROM или заводское |
| RO | `READONLY` | да | нет | нет | Заводское или вычисленное |
| RAM-only | `RAM_ONLY` | да | да | нет | Заводское |

`[R]`

3.3.2. Единственный критерий сохранения параметра ДОЛЖЕН быть определён в одном месте (`ParamFlags::isPersistent`) и использоваться во всех операциях сохранения, загрузки и подсчёта слотов. `[U]`

3.3.3. Флаг `REBOOT` — модификатор, не влияющий на класс: фактическое изменение значения параметра с этим флагом ДОЛЖНО устанавливать запрос перезагрузки (п. 5.6). `[U]`

3.3.4. Параметры RAM-only ДОЛЖНЫ описываться отдельным построителем логического типа; для иных типов RAM-only построители не предусмотрены. `[R]`

3.3.5. Флаг `REBOOT` ДОЛЖЕН быть установлен только у `sys.hw_ver` и `sys.board_type`. Значения остальных параметров могут изменяться в процессе работы системы и применяются без перезагрузки. `[R]` `(р.1.2)`

3.3.6. Подсистема не содержит механизма уведомления потребителей об изменении значений (в коде v1 он отсутствует); способ применения изменённых значений потребителями находится вне области ТЗ. `[R]` `(р.1.2)`

### 3.4. Идентификация

3.4.1. Параметр ДОЛЖЕН адресоваться индексом `uint8_t` в порядке таблицы, диапазон `0 … count − 1`. `[R]`

3.4.2. Индекс НЕ является постоянным идентификатором: между версиями прошивки он может изменяться. `[N]`

3.4.3. Параметр ДОЛЖЕН адресоваться именем (побайтовое сравнение, регистрозависимое). `[R]`

3.4.4. Постоянным идентификатором параметра в хранилище ДОЛЖЕН быть ключ `fnv1a32(name)` (п. 6.5). `[N]`

3.4.5. Индекс элемента рабочего массива RAM ДОЛЖЕН совпадать с индексом соответствующего элемента таблицы ROM. `[R]`

3.4.6. Длина имени параметра НЕ ДОЛЖНА превышать 92 символа (ограничение поля `name` сервиса `GetSet` протокола DroneCAN v0). `[N]` `(р.1.1)`

### 3.5. Допустимость значений

3.5.1. Числовые значения (INT, FLOAT) ДОЛЖНЫ лежать в интервале `[min, max]` включительно. Значение NaN недопустимо. `[R]` `(р.1.1)`

3.5.2. Общее правило допустимости: любое значение параметра ДОЛЖНО принадлежать допустимой области, заданной в описании параметра. Значение вне области НЕ ДОЛЖНО применяться ни при записи через `setValue` (п. 5.3), ни при загрузке из хранилища (п. 7.2): при записи оно отвергается, при загрузке заменяется заводским. `[U]` `(р.1.1)`

3.5.3. Допустимая область строкового параметра: (а) длина не более ёмкости (31 символ в RAM, 27 для persistent) и (б) если для параметра задано допустимое множество — точное регистрозависимое совпадение с одним из его элементов. `[N]` `(р.1.1)`

3.5.4. Допустимое множество значений ДОЛЖНО задаваться в таблице (в ROM). Для `sys.board_type` оно обязательно. `[N]` `(р.1.1)`

3.5.5. Заводское значение каждого параметра ДОЛЖНО принадлежать его допустимой области. `[N]` `(р.1.1)`

3.5.6. Проверка допустимости выполняется независимо для каждого параметра; межпараметрические зависимости подсистемой не проверяются. `[R]` `(р.1.1)`

3.5.7. Логический параметр допускает оба значения. `[R]` `(р.1.1)`

3.5.8. Подсистема проверяет только интервалы `[min, max]` и допустимые множества строк; дискретные наборы допустимых числовых значений (например, режимы шины I2C) проверяются вне подсистемы — в CLI или во внешней программе работы с параметрами. `[R]` `(р.1.2)`

### 3.6. Кодирование версий

3.6.1. Версии (`sys.fw_ver`, `sys.hw_ver`) ДОЛЖНЫ кодироваться 32-битным значением `patch | (minor << 8) | (major << 16)` и храниться как INT. `[R]`

3.6.2. Кодирование ДОЛЖНО вычисляться на этапе компиляции. `[R]`

### 4.1. Размещение и состав

4.1.4. Элемент таблицы ДОЛЖЕН содержать: имя, ключ, тип, флаги, заводское значение, минимум, максимум (для строк — заводскую строку и, при наличии, допустимое множество значений). `[N]` `(р.1.1)`

### 4.2. Построители

4.2.1. Подсистема ДОЛЖНА предоставлять построители элементов таблицы: R/W (`int`, `float`, `bool`, `string`), RAM-only (`bool`), RO (`int`, `float`, `bool`, `string`). `[R]`

4.2.2. R/W-построители ДОЛЖНЫ принимать необязательный аргумент флагов (в частности, `REBOOT`). `[N]`

4.2.3. Все построители ДОЛЖНЫ вычислять ключ на этапе компиляции. `[N]`

4.2.4. Подсистема ДОЛЖНА предоставлять построитель R/W-строки с допустимым множеством значений; множество ДОЛЖНО размещаться в ROM. `[N]` `(р.1.1)`

### 4.3. Независимость от порядка

4.3.1. Порядок элементов в таблице НЕ ДОЛЖЕН влиять на интерпретацию сохранённых данных. `[N]`

4.3.2. Вставка, перестановка и удаление элементов таблицы ДОЛЖНЫ быть допустимы без миграции хранилища. `[N]`

### 4.4. Правила ведения таблицы

4.4.1. Имя параметра является постоянным ключом хранения: переименование эквивалентно удалению старого и добавлению нового параметра, сохранённое значение при этом теряется. `[N]`

4.4.2. Изменение типа persistent-параметра ведёт к использованию заводского значения при загрузке. `[R]`

4.4.3. Правила 4.3–4.4 и 3.1.5 ДОЛЖНЫ быть отражены в комментарии рядом с таблицей. `[R]`

4.4.4. В таблицу, размещённую в заголовке (`inline constexpr`), НЕ ДОЛЖНЫ помещаться значения, зависящие от макросов `__DATE__`, `__TIME__`, `__COUNTER__`: их значения различаются между единицами трансляции (нарушение ODR, итоговое значение определяется выбором компоновщика). Такие значения (в частности `BUILD_STAMP`) присваиваются программно в одной единице трансляции — `ParamRegistry.cpp` (п. 5.9.5). Значения, передаваемые системой сборки как глобальные определения (в частности `GIT_COMMIT_HASH`, п. 5.9.14), допускаются, если одинаковы во всех единицах трансляции. `[N]` `(р.1.5)`

4.4.5. Удаление или переименование параметра, изменение его типа или класса ДОЛЖНЫ блокироваться проверкой CI (п. 10.7–10.14): имена параметров используются внешними приложениями и являются ключами хранения (п. 4.4.1). Алиасы имён настоящим ТЗ не требуются (п. 13.2.5). `[N]` `(р.1.5)`

### 4.5. Проверки на этапе компиляции

Нарушение любого из условий ДОЛЖНО приводить к ошибке компиляции:

4.5.1. Пустое или отсутствующее имя параметра. `[N]`

4.5.2. Ключ, равный `0` или `0xFFFFFFFF` (зарезервированы: `0xFFFFFFFF` — состояние стёртой Flash). `[N]`

4.5.3. Совпадение ключей двух параметров (в том числе дублирование имён). `[N]`

4.5.4. Заводская строка persistent-параметра длиннее 27 символов. `[N]`

4.5.5. Число persistent-параметров превышает ёмкость хранилища в слотах (п. 6.7). `[N]`

4.5.6. Размер слота не равен сумме размеров ключа, тега и данных. `[N]`

4.5.7. Отсутствие в таблице служебного параметра, используемого кодом по compile-time индексу (`ParamIdx::*`). `[N]`

4.5.8. Размер legacy-порядка (п. 7.4) превышает адресуемое пространство формата v1. `[N]`

4.5.9. Длина имени параметра более 92 символов (п. 3.4.6). `[N]` `(р.1.1)`

4.5.10. Заводское значение числового параметра вне его интервала `[min, max]` (п. 3.5.5). `[N]` `(р.1.1)`

4.5.11. Заводское значение строкового параметра не входит в его допустимое множество, либо элемент допустимого множества persistent-параметра длиннее 27 символов (п. 3.5.3, 3.5.5). `[N]` `(р.1.1)`

4.5.12. Нарушение выравнивания области CRC: адрес начала области и её длина должны быть кратны 4 при любом числе слотов (п. 6.6.3). `[N]` `(р.1.1)`

4.5.13. Заводская строка любого строкового параметра (включая RO и RAM-only) длиннее 31 байта. Так, полный хэш коммита Git (40 символов) в `sys.git_hash` не собирается. `[N]` `(р.1.5)`

## 5. Функциональные требования: жизненный цикл и API

### 5.1. Инициализация (`init`)

5.1.1. `init` ДОЛЖЕН вызываться единожды до любого другого обращения к реестру. `[R]`

5.1.2. `init` ДОЛЖЕН выполнять шаги строго в следующем порядке: (а) применить заводские значения ко всем параметрам и вычислить системные параметры (п. 5.9.5); (б) загрузить страницу Flash в теневой буфер; (в) определить формат образа по магическому числу; (г) загрузить, мигрировать или оставить заводские значения по п. 5.1.3–5.1.6; (д) выполнить автоопределение версии платы (п. 5.8). `[R]`

5.1.3. Магия v2 и образ, прошедший проверку (п. 7.1): значения ДОЛЖНЫ применяться по п. 7.2, статус загрузки — `Ok`; запись во Flash НЕ ДОЛЖНА выполняться. `[R]`

5.1.4. Магия v2, но образ не прошёл проверку (число слотов или CRC): НИ ОДНО значение из образа НЕ ДОЛЖНО применяться; параметры остаются заводскими; ДОЛЖЕН выполняться `save()`; статус — `DefaultsBadCount` или `DefaultsBadCrc`. `[N]`

5.1.5. Магия v1: ДОЛЖНА выполняться миграция по п. 7.4, затем `save()` в формате v2; статус — `MigratedFromV1`. `[N]`

5.1.6. Магия иная (стёртая или чужая страница): параметры остаются заводскими, ДОЛЖЕН выполняться `save()`, статус — `DefaultsEmpty`. `[R]`

5.1.7. Параметр, отсутствующий в образе, ДОЛЖЕН сохранить заводское значение. `[R]`

5.1.8. Автоопределение версии платы (п. 5.8) ДОЛЖНО выполняться во всех ветках 5.1.3–5.1.6. `[U]`

5.1.9. Результат загрузки ДОЛЖЕН быть записан в журнал. `[R]`

### 5.2. Чтение

5.2.1. `getByIndex(index)` ДОЛЖЕН возвращать указатель на неизменяемое описание параметра или `nullptr`, если индекс вне диапазона. `[R]`

5.2.2. `getByName(name)` ДОЛЖЕН возвращать указатель на описание параметра или `nullptr`, если имя не найдено. `[R]`

5.2.3. `count()` ДОЛЖЕН возвращать общее число параметров (включая RO и RAM-only). `[R]`

5.2.4. Операции чтения НЕ ДОЛЖНЫ изменять состояние реестра, обращаться к хранилищу и пересчитывать системные параметры; доступ по индексу — O(1). `[U]` `(р.1.4)`

5.2.5. Аксессоры значения ДОЛЖНЫ приводить тип по правилам:

| Аксессор | INT | FLOAT | BOOL | STRING |
| :--- | :--- | :--- | :--- | :--- |
| `asInt` | значение | усечение к нулю | 0 / 1 | не определён |
| `asFloat` | приведение | значение | 0.0 / 1.0 | не определён |
| `asBool` | `≠ 0` | `≠ 0.0` | значение | не определён |
| `asString` | `""` | `""` | `""` | C-строка |

Для STRING числовые аксессоры не определены: вызывающий код проверяет `isString()`. `[R]`

### 5.3. Запись значения (`setValue`)

5.3.1. `setValue(index, value)` ДОЛЖЕН изменять только значение в RAM и НЕ ДОЛЖЕН обращаться к хранилищу. `[R]`

5.3.2. При `index ≥ count` ДОЛЖЕН возвращаться `false`. `[R]`

5.3.3. Для RO-параметра ДОЛЖЕН возвращаться `false`. `[R]`

5.3.4. Входное значение ДОЛЖНО неявно приводиться к типу параметра: целое ↔ вещественное (вещественное → целое усечением к нулю), логическое → 0/1 (или 0.0/1.0), число → логическое как `≠ 0`. Причина: DroneCAN может передать число другим типом, чем объявлен параметр. `[R]`

5.3.5. Передача строки в числовой или логический параметр, а также числа или логического значения в строковый параметр ДОЛЖНА приводить к `false` без изменения состояния (обращение к неактивной альтернативе `variant` недопустимо, п. 2.5.5). `[U]`

5.3.6. Для INT и FLOAT значение вне `[min, max]` ДОЛЖНО приводить к `false`. `[R]`

5.3.7. Для BOOL проверка пределов не выполняется. `[R]`

5.3.8. Для persistent STRING строка длиннее 27 символов ДОЛЖНА отвергаться (`false`) с записью в журнал. `[N]`

5.3.9. Для STRING-параметра с допустимым множеством значение вне множества ДОЛЖНО отвергаться (`false`) с записью в журнал. Для `sys.board_type` множество: `lts-5l-generic`, `lts-5l-p5`, `lts-5l-k4`, `lts-5l-u4`, `lts-5l-k3`. `[R]` `(р.1.1)`

5.3.10. При фактическом изменении значения параметра с флагом `REBOOT` ДОЛЖЕН устанавливаться запрос перезагрузки. Запись того же значения запрос НЕ ДОЛЖНА устанавливать. `[R]`

5.3.11. Успешная запись (включая запись равного значения) ДОЛЖНА возвращать `true`. `[R]`

5.3.12. При возврате `false` значение параметра НЕ ДОЛЖНО изменяться. `[R]`

### 5.4. Сохранение (`save`)

5.4.1. `save` ДОЛЖЕН записывать в хранилище все persistent-параметры в формате раздела 6, полностью заменяя прежнее содержимое области реестра. `[R]`

5.4.2. RO и RAM-only параметры НЕ ДОЛЖНЫ записываться. `[R]`

5.4.3. Перед стиранием и записью страницы ДОЛЖЕН сбрасываться сторожевой таймер. `[R]`

5.4.4. Перенос данных из теневого буфера во Flash ДОЛЖЕН выполняться одной операцией записи страницы. `[R]`

5.4.5. После записи ДОЛЖНО выполняться контрольное чтение страницы и проверка заголовка и CRC; результат ДОЛЖЕН возвращаться как `bool`. `[N]`

5.4.6. Неуспех контрольной проверки ДОЛЖЕН фиксироваться в журнале. `[N]`

5.4.7. `save` НЕ ДОЛЖЕН изменять значения параметров в RAM. `[R]`

5.4.8. Запись в хранилище НЕ ДОЛЖНА выполняться автоматически при `setValue`; сохранение инициируется явным вызовом `save` (в частности, командой CLI или командой SAVE по CAN). `[R]`

5.4.9. `save` НЕ ДОЛЖЕН стирать и программировать страницу, если сформированный образ побайтово совпадает с текущим содержимым Flash; в этом случае `save` возвращает результат проверки образа (п. 7.1), а сохранение считается выполненным. Причина: внешнее приложение при каждом старте сравнивает и записывает параметры (значение `float` из конфигурации может не совпасть с `float32` платы) и затем подаёт SAVE. `[N]` `(р.1.6)`

### 5.5. Сброс к заводским значениям (`resetToDefaults`)

5.5.1. `resetToDefaults` ДОЛЖЕН: применить заводские значения всех параметров (включая вычисление системных, п. 5.9.5), выполнить `save()` и установить запрос перезагрузки. `[R]` `(р.1.4)`

5.5.2. `resetToDefaults` ДОЛЖЕН возвращать результат `save()` (`bool`); обработчик команды ERASE применяет к нему то же правило, что обработчик SAVE (п. 5.6.8): при неуспехе — `ok = false`, перезагрузка не выполняется. `[N]` `(р.1.7)`

### 5.6. Запрос перезагрузки

5.6.1. Подсистема ДОЛЖНА предоставлять `isRebootRequired()` и `clearRebootRequired()`. `[R]`

5.6.2. Запрос перезагрузки ДОЛЖЕН сниматься только явным вызовом `clearRebootRequired()`. `[R]`

5.6.3. Переопределение значения при автоопределении версии платы на старте (п. 5.8) НЕ ДОЛЖНО устанавливать запрос перезагрузки. Обоснование: в v1 такое переопределение выполнялось через `setValue` и поднимало флаг при каждом старте платы с отличающейся аппаратной версией, вследствие чего любая последующая команда сохранения приводила к перезагрузке. `[U]`

5.6.4. Подсистема НЕ ДОЛЖНА инициировать перезагрузку самостоятельно. Перезагрузку выполняет вызывающий код по команде сохранения (CAN: SAVE, ERASE; CLI: команды сохранения и сброса) при `isRebootRequired() == true`. `[R]` `(р.1.1)`

5.6.5. Запрос перезагрузки хранится только в RAM и сбрасывается при старте. `[R]` `(р.1.1)`

5.6.6. Новое значение параметра с флагом `REBOOT` (в частности `sys.board_type`) действует на систему только после перезагрузки: до неё изменяется лишь значение в реестре. `[R]` `(р.1.2)`

5.6.7. При команде сохранения (CAN: SAVE и ERASE; CLI: эквивалентные команды) вызывающий код ДОЛЖЕН выполнять по порядку: (а) `save()` (для ERASE — `resetToDefaults()`); (б) постановку ответа на команду в очередь передачи (`ok` = результат сохранения); (в) при успехе и `isRebootRequired() == true` — запрос отложенной перезагрузки у службы (п. 5.6.12) с одновременным сбросом запроса перезагрузки (`clearRebootRequired()`); (г) дальнейшее выполняет служба по п. 5.6.13: ожидание опустошения очередей передачи CAN, выдержка `REBOOT_DELAY_MS = 1500` мс (`Config::System`), `Serial.flush()`, пауза `FLUSH_DELAY_MS = 10` мс для опустошения буферов UART и программный сброс `NVIC_SystemReset()`. Ответ на команду ДОЛЖЕН уйти до сброса. `[R]` `(р.1.8)`

5.6.8. Если `save()` вернул `false`, перезагрузка НЕ ДОЛЖНА выполняться, выдержка не запускается, запрос перезагрузки НЕ сбрасывается, а ответ на команду ДОЛЖЕН содержать `ok = false`. Плата продолжает работу на значениях в RAM; приложение может повторить сохранение, и успешное повторное сохранение приведёт к перезагрузке. `[N]` `(р.1.7)`

5.6.9. Запись параметров через `GetSet`, в том числе `sys.board_type` и `sys.hw_ver`, сама перезагрузку не вызывает. Порядок записи параметров с флагом `REBOOT` относительно остальных значения не имеет: все значения применяются в RAM, а сохранение и перезагрузка выполняются одной командой SAVE. `[R]` `(р.1.6)`

5.6.10. Реестр ДОЛЖЕН поддерживать блокировку записи (`lockWrites`, `isWriteLocked`): пока она включена, `setValue()` и `resetToDefaults()` возвращают `false` без каких-либо изменений (`resetToDefaults` не применяет заводские значения и не пишет во Flash); чтение и `save()` остаются допустимыми (при неизменном образе `save()` запись не выполняет, п. 5.4.9). Блокировку включает служба отложенной перезагрузки в момент запроса (п. 5.6.12); снимается она только сбросом МК. Блокировка действует одинаково для CAN и CLI, так как изменения, принятые после успешного сохранения, будут потеряны сбросом. `[N]` `(р.1.8)`

5.6.11. Сброс выполняется программно (`NVIC_SystemReset`), а не сторожевым таймером; причина сброса в журнале загрузки после него — программный сброс. `[R]` `(р.1.7)`

5.6.12. Отложенную перезагрузку выполняет отдельная служба прикладного уровня, не входящая ни в `ParamRegistry`, ни в `CanManager`. Служба принимает запрос от обработчиков CAN и CLI (`requestDelayedReboot`), включает блокировку записи (п. 5.6.10) и обслуживается вызовом тика в конце `loop()` независимо от `Config::CanTxEnable` и наличия шины CAN. Зависимость от CAN — только через предикат готовности очередей передачи, который регистрирует CAN-слой; если передача выключена или шины нет, предикат не задан и ожидание опустошения пропускается. `[N]` `(р.1.8)`

5.6.13. Ожидание опустошения очередей передачи CAN ДОЛЖНО быть ограничено `REBOOT_TX_DRAIN_TIMEOUT_MS = 1000` мс. Очередями считаются программная очередь `libcanard` (`canardPeekTxQueue() == nullptr`) и аппаратный FIFO FDCAN (`HAL_FDCAN_GetTxFifoFreeLevel()` равен размеру FIFO `TxFifoQueueElmtsNbr`). Опустошение фиксируется однократно (защёлка): отсчёт `REBOOT_DELAY_MS` начинается при первом наблюдении пустых очередей после запроса и НЕ сбрасывается последующим появлением кадров (периодические сообщения). Если очереди не опустели за `REBOOT_TX_DRAIN_TIMEOUT_MS` (например, кадры не подтверждаются на шине), отсчёт начинается принудительно. Максимальная задержка от запроса до сброса — `REBOOT_TX_DRAIN_TIMEOUT_MS + REBOOT_DELAY_MS` плюс `FLUSH_DELAY_MS`. `[N]` `(р.1.8)`

### 5.7. Диагностика

5.7.1. Подсистема ДОЛЖНА хранить и предоставлять статус последней загрузки `loadStatus()` со значениями: `Ok`, `MigratedFromV1`, `DefaultsEmpty`, `DefaultsBadCount`, `DefaultsBadCrc`. `[N]`

5.7.2. `print()` ДОЛЖЕН выводить в журнал по каждому параметру: индекс, имя, значение и признак `[RO]` (для RO) или `[MODIFIED]` (значение отличается от заводского). `[R]`

5.7.3. Форматирование чисел в `print()` НЕ ДОЛЖНО использовать `%lld` и `%f`: 64-битные значения выводятся разбиением на старшую и младшую части, FLOAT — с тремя знаками после запятой ручным форматированием. `[R]`

5.7.4. Значения `sys.fw_ver` и `sys.hw_ver` ДОЛЖНЫ выводиться как `vX.Y.Z` и `vX.Y` соответственно. `[R]`

### 5.8. Автоопределение версии платы

5.8.1. Если `sys.hw_autodetect = true`, после загрузки значений ДОЛЖНА вызываться `Bsp_AutoDetectHwVersion(board_type, current_hw_ver)`. `[R]`

5.8.2. Если результат отличается от текущего значения `sys.hw_ver`, значение в RAM ДОЛЖНО быть переопределено результатом. Подсистема НЕ ДОЛЖНА записывать переопределение во Flash самостоятельно; при последующем явном `save()` переопределённое значение сохраняется как обычное значение параметра. `[R]` `(р.1.1)`

5.8.3. Если результат вне `[min, max]` параметра, он ДОЛЖЕН быть применён принудительно. `[R]`

5.8.4. Факт переопределения ДОЛЖЕН фиксироваться в журнале. `[R]`

### 5.9. Системные параметры

5.9.1. `sys.param_count` ДОЛЖЕН содержать общее число параметров прошивки. `[R]`

5.9.2. `sys.fw_ver`, `sys.stamp`, `sys.is_debug` ДОЛЖНЫ отражать константы сборки; формат `sys.stamp` — п. 5.9.12. `[R]` `(р.1.4)`

5.9.3. `sys.uid` — RO-строка, заполняемая из уникального идентификатора кристалла (три 32-битных слова, формат `%08lX-%08lX-%08lX`, 26 символов); в среде QEMU — `QEMU-EMULATED-00000000`. `[R]`

5.9.4. `sys.payload_type` — информационная RO-строка с названием текущей нагрузки (русскоязычный текст в UTF-8, например «БЕЗ НАГРУЗКИ»). Тип нагрузки однозначно определяется значением `sys.board_type` (тип платы и нагрузки связаны взаимно однозначно). Значение устанавливается драйвером нагрузки при его инициализации (`PayloadDriver::init()`), после инициализации реестра и применения `sys.board_type`. `[R]` `(р.1.2)`

5.9.5. Вычисляемые системные параметры (`sys.param_count`, `sys.stamp`, `sys.uid`) ДОЛЖНЫ вычисляться подсистемой один раз при применении заводских значений (`init`, `resetToDefaults`) и оставаться актуальными без пересчёта при чтении. Значения `sys.fw_ver` и `sys.is_debug` берутся из таблицы. Все значения известны в момент применения заводских значений (приложение H): `sys.param_count` — константа компиляции; `sys.stamp` — `BUILD_STAMP`, константа компиляции, присваиваемая в `ParamRegistry.cpp` (п. 4.4.4); `sys.uid` определяется регистрами MCU (п. 8.2.2). Служебные параметры адресуются compile-time индексами, без поиска по таблице. `[U]` `(р.1.4)`

5.9.6. Перечень и атрибуты системных параметров приведены в приложении A. `[R]`

5.9.7. Значением `sys.board_type` по умолчанию ДОЛЖЕН быть безопасный тип `lts-5l-generic`. `[R]` `(р.1.1)`

5.9.8. Тип `lts-5l-generic` ДОЛЖЕН соответствовать штатной работе без кода, зависящего от типа нагрузки; параметры и их значения при этом остаются доступными. `[R]` `(р.1.1)`

5.9.9. Невалидное значение `sys.board_type` (вне допустимого множества) при загрузке из хранилища ДОЛЖНО заменяться заводским значением `lts-5l-generic` (п. 3.5.2). `[U]` `(р.1.1)`

5.9.10. Запись значения в RO-параметр `sys.payload_type` выполняется драйвером нагрузки снятием `const` с указателя, полученного из `getByName`: `const_cast<Param*>( registry->getByName( "sys.payload_type" ) )->value = ParamString( name )`. Подсистема ДОЛЖНА сохранять этот контракт: указатель `getByName` ссылается на изменяемый элемент реестра в RAM (не на const-объект и не на ROM); `refreshSysParams()` значение `sys.payload_type` не изменяет; значение хранится только в RAM и не сохраняется; `applyDefaults()` (в составе `resetToDefaults()`) сбрасывает его до следующего старта. Замена на явный метод установки системных значений настоящим ТЗ не требуется. `[R]` `(р.1.2)`

5.9.11. Значение, записываемое в `sys.payload_type`, ДОЛЖНО умещаться в 31 байт (ёмкость `ParamString`) с учётом UTF-8; усечение посреди многобайтного символа недопустимо. Контроль длины выполняется на стороне драйвера нагрузки (литералы СЛЕДУЕТ проверять при компиляции). Строка информационная и в хранилище не сохраняется. `[N]` `(р.1.2)`

5.9.12. Значение `sys.stamp` равно `BUILD_STAMP` из `version.h`: десятичное число `ГГГГММДД × 10^6 + ЧЧММСС` (например, `20260919183241`), тип `uint64_t`; превышает диапазон `int32` и выводится в `print()` по п. 5.7.3. Значение отражает момент компиляции единицы трансляции `ParamRegistry.cpp`, а не момент компоновки прошивки; оно не совпадает по формату с `FirmwareMeta` (строка `Stamp` журнала) и при локальной инкрементальной сборке может отставать от него; выпускная сборка выполняется полностью на билд-машине (п. 10.14). `[R]` `(р.1.5)`

5.9.13. Подсистема ДОЛЖНА содержать RO-параметр `sys.git_hash` (STRING): идентификатор коммита Git, из которого собрана прошивка; в EEPROM не сохраняется. `[N]` `(р.1.5)`

5.9.14. Значение ДОЛЖНО задаваться системой сборки как глобальное определение препроцессора `GIT_COMMIT_HASH` (строковый литерал), одинаковое во всех единицах трансляции, и подставляться в таблицу. В отличие от `BUILD_STAMP` (п. 4.4.4), размещение в таблице заголовка допустимо, так как значение одинаково во всех единицах. Если определение отсутствует, значение — `unknown`. `[N]` `(р.1.5)`

5.9.15. Формат значения: сокращённый хэш коммита, СЛЕДУЕТ 12 символов в нижнем регистре шестнадцатеричных цифр; при незафиксированных изменениях рабочего дерева ДОЛЖЕН добавляться суффикс `-dirty`; при отсутствии сведений о Git — `unknown`. Длина не более 31 байта (ёмкость `ParamString`); полный хэш SHA-1 не помещается (п. 4.5.13). `[N]` `(р.1.5)`

5.9.16. Значение `sys.git_hash` СЛЕДУЕТ выводить в журнал загрузки рядом с версией прошивки; в `print()` он выводится как любой RO-параметр. `[N]` `(р.1.5)`

## 6. Формат хранения (нормативный)

### 6.1. Общие положения

6.1.1. Хранилище — одна страница Flash, эмулирующая EEPROM через теневой буфер RAM размером `E2END + 1` байт. `[R]`

6.1.2. Все операции чтения и записи значений ДОЛЖНЫ выполняться через теневой буфер; `fill` ДОЛЖЕН предшествовать чтению и записи, `flush` фиксирует буфер во Flash. `[R]`

6.1.3. Многобайтовые поля ДОЛЖНЫ храниться в порядке little-endian (нативный порядок Cortex-M). `[R]`

6.1.4. Область страницы принадлежит подсистеме целиком. `[N]`

### 6.2. Заголовок (12 байт)

6.2.1. Заголовок ДОЛЖЕН располагаться с адреса 0 и иметь раскладку:

| Смещение | Размер | Поле | Значение |
| :---: | :---: | :--- | :--- |
| 0 | 4 | `magic` | `0x50415232` («PAR2») |
| 4 | 4 | `crc32` | CRC области по п. 6.6 |
| 8 | 2 | `count` | Число слотов `N` |
| 10 | 2 | `reserved` | `0` |

`[N]`

6.2.2. Поле `reserved` ДОЛЖНО записываться нулём; при чтении его значение не интерпретируется, но входит в область CRC. `[N]`

6.2.3. Слоты ДОЛЖНЫ начинаться с адреса 12. `[N]`

### 6.3. Слот (32 байта)

6.3.1. Слот ДОЛЖЕН иметь раскладку:

| Смещение | Размер | Поле | Описание |
| :---: | :---: | :--- | :--- |
| 0 | 4 | `hash` | Ключ параметра |
| 4 | 1 | `tag` | Тип значения |
| 5 | 27 | `data` | Данные |

`[N]`

6.3.2. Неиспользуемые байты `data` ДОЛЖНЫ записываться нулями. `[N]`

6.3.3. Слоты ДОЛЖНЫ располагаться подряд без промежутков; порядок слотов не несёт смысла. `[N]`

### 6.4. Кодирование значений

6.4.1. Тег типа ДОЛЖЕН принимать значения: `0` — INT, `1` — FLOAT, `2` — BOOL, `3` — STRING; значения зафиксированы и не зависят от порядка альтернатив в контейнере значений. `[U]`

6.4.2. INT — 8 байт `data[0..7]`, знаковое, little-endian. `[R]`

6.4.3. FLOAT — 4 байта `data[0..3]`, IEEE 754 binary32. `[R]`

6.4.4. BOOL — 1 байт `data[0]`: `0` или `1`; при чтении любое ненулевое значение трактуется как `true`, чтение байта непосредственно в переменную типа `bool` не допускается. `[U]`

6.4.5. STRING — до 27 байт `data[0..26]`, дополнение нулями; завершающий нуль не требуется; при чтении длина ограничивается 27 байтами, результат завершается нулём принудительно. `[U]`

### 6.5. Ключ параметра

6.5.1. Ключ ДОЛЖЕН вычисляться как FNV-1a 32 бит от байтов имени без завершающего нуля: начальное значение `2166136261` (`0x811C9DC5`); для каждого байта — `hash ^= byte; hash *= 16777619` (`0x01000193`) с арифметикой по модулю `2^32`. `[N]`

6.5.2. Значения ключа `0` и `0xFFFFFFFF` ДОЛЖНЫ быть зарезервированы и недопустимы для параметров. `[N]`

### 6.6. Контрольная сумма

6.6.1. Контрольная сумма ДОЛЖНА определяться как CRC-32/STM32 (слова): полином `0x04C11DB7`, начальное значение `0xFFFFFFFF`, без отражения входа и выхода, без финального XOR. Область CRC рассматривается как последовательность 32-битных слов в порядке возрастания адресов; каждое слово собирается из 4 байт в порядке little-endian и обрабатывается от старшего бита к младшему (`crc ^= word`, затем 32 сдвига влево с условным XOR полинома). Это результат блока CRC микроконтроллера STM32 в конфигурации по умолчанию при вводе слов (`CRC_INPUTDATA_FORMAT_WORDS`), совпадающий с контролем целостности прошивки. Требование задаёт результат, а не способ вычисления. `[N]` `(р.1.2)`

6.6.2. CRC ДОЛЖНА считаться по непрерывной области `[8, 12 + 32·N)`: `count`, `reserved` и все слоты. Магия, поле `crc32` и хвост страницы в область не входят. `[N]`

6.6.3. Область CRC ДОЛЖНА быть выровнена по слову: адрес начала (8) кратен 4, длина `4 + 32·N` кратна 4 при любом `N`. Это свойство формата ДОЛЖНО сохраняться при изменениях раскладки (п. 4.5.12), чтобы расчёт по 32-битным словам применялся без дополнения области. `[N]` `(р.1.1)`

6.6.4. Допускаются две реализации, дающие бит-в-бит одинаковый результат: (а) программная (пословная, табличная или бестабличная); (б) аппаратная — CRC-периферия STM32G4 в режиме ввода слов. Выбор реализации НЕ ДОЛЖЕН влиять на формат образа. `[N]` `(р.1.1)`

6.6.5. Аппаратная реализация ДОЛЖНА использовать конфигурацию блока CRC, применяемую в контроле целостности прошивки: полином по умолчанию (`DEFAULT_POLYNOMIAL_ENABLE`, `0x04C11DB7`), начальное значение по умолчанию (`DEFAULT_INIT_VALUE_ENABLE`, `0xFFFFFFFF`), инверсия входа и выхода отключена (`CRC_INPUTDATA_INVERSION_NONE`, `CRC_OUTPUTDATA_INVERSION_DISABLE`), формат ввода — слова (`CRC_INPUTDATA_FORMAT_WORDS`). Результат `HAL_CRC_Calculate` используется без дополнительных преобразований. Слова формируются из байтов области в порядке little-endian: байт с меньшим адресом — младший байт слова. `[N]` `(р.1.2)`

6.6.6. Реализация ДОЛЖНА быть скрыта за единственной функцией расчёта CRC над диапазоном адресов теневого буфера; остальной код подсистемы не зависит от способа вычисления. `[N]` `(р.1.1)`

6.6.7. Эквивалентность программной и аппаратной реализаций ДОЛЖНА подтверждаться тестом на оборудовании (TC-36) на реальных образах и на буферах с числом байтов, кратным 4. `[N]` `(р.1.1)`

6.6.8. Контрольные векторы (получены эталонной программной реализацией по п. 6.6.1; аппаратное совпадение подтверждается TC-36): слово `0x12345678` → `0xDF8A8A2B`; слово `0x00000000` → `0xC704DD7B`; слова `0x12345678`, `0x9ABCDEF0` → `0x7D24A31B`; область из 68 байт `02 00 00 00`, затем байты `00 01 02 … 3F` → `0x67C51B02`. `[N]` `(р.1.2)`

6.6.9. В среде QEMU (`Bsp_IsRunningInQemu()`) и в тестах на хосте ДОЛЖНА использоваться программная реализация: аппаратный блок CRC в этих средах не применяется (как и в контроле целостности прошивки). Образ, записанный на оборудовании с аппаратным CRC, ДОЛЖЕН проходить проверку программной реализацией без изменений. `[N]` `(р.1.2)`

6.6.10. Образ без слотов (`count = 0`) ДОЛЖЕН иметь `crc32 = 0xC704DD7B` (область — одно слово `0x00000000`). `[N]` `(р.1.2)`

### 6.7. Ёмкость

6.7.1. Максимальное число слотов: `MAX_SLOTS = ⌊(E2END + 1 − 12) / 32⌋`; при `E2END + 1 = 2048` — 63. `[N]`

### 6.8. Хвост страницы

6.8.1. Байты страницы от конца последнего слота до конца теневого буфера ДОЛЖНЫ записываться значением `0xFF`. `[N]`

## 7. Алгоритмы (нормативные)

### 7.1. Проверка образа

7.1.1. Проверка ДОЛЖНА выполнять последовательно: (а) чтение `magic` и сравнение с `0x50415232`; несовпадение — результат `DefaultsEmpty`; (б) чтение `count`; `count > MAX_SLOTS` — результат `DefaultsBadCount`; (в) вычисление CRC по п. 6.6 и сравнение с `crc32`; несовпадение — результат `DefaultsBadCrc`; (г) иначе — `Ok`. `[N]`

7.1.2. Проверка НЕ ДОЛЖНА изменять параметры реестра. `[N]`

### 7.2. Загрузка значений

7.2.1. Загрузка ДОЛЖНА начинаться с проверки образа (п. 7.1); при результате, отличном от `Ok`, значения не применяются. `[N]`

7.2.2. Для каждого слота `k = 0 … count − 1` ДОЛЖНО выполняться: (а) прочитать ключ; (б) найти параметр таблицы с этим ключом; если не найден (параметр удалён из прошивки), слот пропускается; (в) если найденный параметр не persistent (стал RO или RAM-only), слот пропускается; (г) если тег не совпадает с типом параметра, заводское значение сохраняется; (д) иначе значение декодируется по п. 6.4 и проверяется на принадлежность допустимой области по п. 3.5 (числовой интервал; для строк — длина и допустимое множество); значение вне области заменяется заводским. `[N]` `(р.1.1)`

7.2.3. При повторении ключа в образе ДОЛЖЕН применяться последний из повторяющихся слотов. `[N]`

7.2.4. Пропущенные слоты не ДОЛЖНЫ приводить к ошибке загрузки. `[N]`

### 7.3. Сохранение

7.3.1. Сохранение ДОЛЖНО выполнять: (а) заполнить теневой буфер содержимым Flash (`fill`); (б) для каждого persistent-параметра записать слот (п. 6.3–6.4) с ключом из таблицы, слоты — подряд с адреса 12; (в) записать хвост `0xFF` (п. 6.8); (г) записать `count` и `reserved = 0`; (д) вычислить CRC по п. 6.6 над содержимым теневого буфера и записать `crc32`; (е) записать `magic`; (ж) сбросить сторожевой таймер; (з) выполнить `flush`; (и) перечитать страницу (`fill`) и выполнить проверку по п. 7.1; результат — успех, если проверка вернула `Ok` и `count` совпал с записанным. `[N]`

7.3.2. Строка длиннее 27 байт при записи слота ДОЛЖНА усекаться до 27 байт (защитное условие, недостижимое при соблюдении п. 5.3.8). `[N]`

7.3.3. Два последовательных сохранения без изменения значений ДОЛЖНЫ давать побайтово идентичные образы. `[N]`

7.3.4. Изменение образа ДОЛЖНО определяться при записи в теневой буфер: каждый записываемый байт сравнивается с прежним значением, загруженным `fill` в начале `save`; запись байта и признак изменения — только при несовпадении. Если изменений нет, пункты (ж) и (з) п. 7.3.1 (сброс IWDG и `flush`) и перечитывание пропускаются, а проверка (и) выполняется над теневым буфером, равным содержимому Flash. Различия, вызванные повреждением Flash или остатками прежнего образа (в том числе за концом слотов), обнаруживаются тем же сравнением и приводят к записи. `[N]` `(р.1.6)`

### 7.4. Миграция формата v1

7.4.1. Формат v1: магия `0x5041524D` («PARM») по адресу 0; слоты с адреса 4, размер слота 32 байта (тег 1 байт + данные 31 байт); адрес слота определяется порядковым номером persistent-параметра. `[R]`

7.4.2. Миграция ДОЛЖНА использовать замороженный список ключей `LegacyV1::ORDER`: элемент с номером `k` — параметр, размещавшийся в `k`-м слоте v1. `[N]`

7.4.3. Список порядка ДОЛЖЕН формироваться по таблице последнего релиза с форматом v1 и НЕ ДОЛЖЕН изменяться после этого. `[N]`

7.4.4. Для каждого элемента списка ДОЛЖНО выполняться: найти параметр по ключу (не найден — пропуск); если параметр не persistent — пропуск; прочитать слот v1 и применить значение по правилам 7.2.2(г)–(д) с учётом данных длиной 31 байт. `[N]`

7.4.5. Слот v1, находящийся за границей буфера, ДОЛЖЕН пропускаться. `[N]`

7.4.6. После миграции ДОЛЖЕН выполняться `save()` в формате v2 (п. 5.1.5). `[N]`

7.4.7. Строка v1 длиннее 27 символов ДОЛЖНА усекаться при последующем сохранении (п. 7.3.2). `[N]`

### 7.5. Обработка нештатных состояний

| Состояние образа | Действие | Статус | Запись во Flash |
| :--- | :--- | :--- | :---: |
| Магия v2, `count` и CRC верны | Применить слоты | `Ok` | нет |
| Магия v2, `count > MAX_SLOTS` | Заводские значения | `DefaultsBadCount` | да |
| Магия v2, CRC не совпала | Заводские значения | `DefaultsBadCrc` | да |
| Магия v1 | Миграция | `MigratedFromV1` | да |
| Иная магия | Заводские значения | `DefaultsEmpty` | да |

7.5.1. Поведение подсистемы в нештатных состояниях ДОЛЖНО соответствовать таблице. `[N]`

7.5.2. Подсистема НЕ ДОЛЖНА применять значения из образа, не прошедшего проверку. `[N]`

## 8. Требования к интерфейсам

### 8.1. Драйвер хранилища (`stm32_eeprom`)

8.1.1. Подсистема ДОЛЖНА использовать только операции драйвера: `eeprom_buffer_fill()` (страница Flash → теневой буфер), `eeprom_buffered_read_byte(pos)`, `eeprom_buffered_write_byte(pos, value)`, `eeprom_buffer_flush()` (теневой буфер → Flash со стиранием страницы). `[R]`

8.1.2. Ёмкость буфера определяется макросом `E2END`; его отсутствие ДОЛЖНО приводить к ошибке компиляции. `[N]`

8.1.3. Операция `flush` считается блокирующей, длительность порядка 25 мс. `[R]`

8.1.4. Страница хранилища расположена по адресу `0x0807F800`, размер страницы 2048 байт (по журналу загрузки), что соответствует `E2END + 1 = 2048` и `MAX_SLOTS = 63`. `[R]` `(р.1.1)`

8.1.5. Страница хранилища НЕ ДОЛЖНА входить в образ прошивки (сценарий компоновщика) и в область контроля целостности прошивки: изменение параметров не должно нарушать контроль целостности. `[N]` `(р.1.1)`

8.1.6. Драйвер хранилища ДОЛЖЕН передавать подсистеме всю страницу целиком; иные потребители страницы отсутствуют (п. 6.1.4, 13.2.1). `[R]` `(р.1.1)`

### 8.2. BSP

8.2.1. `Bsp_AutoDetectHwVersion(board_type, current_raw)` принимает C-строку типа платы и текущую версию в кодировке 3.6.1, возвращает версию в той же кодировке. `[R]`

8.2.2. `Bsp_IsRunningInQemu()` возвращает признак исполнения в эмуляторе. Признак определяется только регистрами MCU: чтением `DBGMCU->IDCODE` после включения `DEMCR.TRCENA`; значение «эмулятор» соответствует условию «`DEV_ID` не равен STM32G431 и STM32G474». Функция не зависит от порядка инициализации BSP и может вызываться на любом этапе загрузки. `[R]` `(р.1.3)`

8.2.3. Вызов `Bsp_IsRunningInQemu()` устанавливает бит `DEMCR.TRCENA`; повторные вызовы безопасны. На реальном кристалле другого семейства (иной `DEV_ID`) будут выбраны заглушка `sys.uid` и программная реализация CRC — результат CRC при этом корректен (п. 6.6.4). `[R]` `(р.1.3)`

### 8.5. Информация о сборке и конфигурации

8.5.1. Подсистема использует константы `MAJOR`, `MINOR`, `PATCH`, `BUILD_STAMP` (`version.h`), `GIT_COMMIT_HASH` (определение системы сборки), `Config::DebugSensors`, `Config::System::MIN_VDD_MV` и адрес идентификатора кристалла `UID_BASE`. `[R]` `(р.1.5)`

### 8.6. ETL

8.6.2. Программная реализация CRC — собственная функция пословного расчёта (п. 6.6.1, приложение G) либо `etl::crc32_mpeg2` при подаче байтов каждой четырёхбайтной группы в обратном порядке (если этот тип есть в используемой версии ETL). `etl::crc32` (CRC-32/ISO-HDLC) п. 6.6.1 НЕ соответствует. ### 8.7. Внешние потребители

8.7.1. CLI и DroneCAN используют интерфейс из п. 5.2–5.7 (`getByIndex`, `getByName`, `setValue`, `save`, `resetToDefaults`, `print`, `isRebootRequired`, `clearRebootRequired`, `loadStatus`). `[R]`

8.7.2. Внешний код НЕ ДОЛЖЕН опираться на физические адреса параметров в EEPROM; поле физического адреса в описании параметра отсутствует. `[N]`

8.7.3. Устройство использует DroneCAN v0 (libcanard v0.2, классический CAN, без FD). `[R]` `(р.1.1)`

8.7.4. Сервис `GetSet`: параметр ДОЛЖЕН выбираться по имени, если имя в запросе непустое, иначе по индексу. `[R]` `(р.1.6)`

8.7.5. Соответствие типов значений: INT — `integer_value` (int64), FLOAT — `real_value` (float32), BOOL — `boolean_value`, STRING — `string_value`. Ответ `GetSet` ДОЛЖЕН содержать текущее значение, заводское значение и (для числовых параметров) минимум и максимум. `[R]` `(р.1.1)`

8.7.6. Ответ `GetSet` ДОЛЖЕН всегда содержать фактическое значение параметра после обработки запроса: при отказе (`setValue` вернул `false`, параметр RO, значение вне допустимой области, запрет записи в специальном режиме) возвращается неизменённое значение. Внешнее приложение определяет принятие записи сравнением запрошенного и возвращённого значений. `[U]` `(р.1.6)`

8.7.7. Сервис `ExecuteOpcode`: SAVE — вызов `save()`, ERASE — вызов `resetToDefaults()`; признак успеха ответа СЛЕДУЕТ формировать по возвращаемому значению `save()`. После выполнения при `isRebootRequired() == true` перезагрузку выполняет вызывающий код (п. 5.6.4). `[R]` `(р.1.1)`

8.7.8. Длина строкового значения (до 31 символа) не превышает предела протокола; длина имени параметра — п. 3.4.6. `[N]` `(р.1.1)`

8.7.9. Внешнее приложение проверяет целостность конфигурации самостоятельно (например, чтением параметров после SAVE); подсистема не обеспечивает дополнительной проверки на стороне CAN. `[R]` `(р.1.1)`

8.7.10. Команды CLI, сохраняющие и сбрасывающие параметры, ДОЛЖНЫ использовать тот же путь (`save`, `resetToDefaults`) и то же правило перезагрузки. `[R]` `(р.1.1)`

8.7.11. Прошивка ДОЛЖНА отвечать на каждый принятый запрос `GetSet` и `ExecuteOpcode`; оставлять запрос без ответа НЕ ДОЛЖНО. Для запроса без результата — несуществующее имя, индекс вне диапазона, имя длиннее 92 байт, ошибка декодирования — ответ `GetSet` пустой: пустое имя, пустое значение, пустые заводское значение, минимум и максимум. На неизвестный код операции `ExecuteOpcode` отвечает с `ok = false`. `[U]` `(р.1.6)`

8.7.12. Имя в запросе длиннее 92 байт НЕ ДОЛЖНО усекаться: параметр считается ненайденным (п. 8.7.11). Длины имён в таблице не превышают 92 байт (п. 3.4.6). `[U]` `(р.1.6)`

8.7.13. Реестр ДОЛЖЕН предоставлять поиск индекса по имени (`findIndex`: индекс либо признак отсутствия); обработчики CAN и CLI НЕ ДОЛЖНЫ выполнять собственный перебор. `[N]` `(р.1.6)`

8.7.14. Индекс параметра в обработчиках ДОЛЖЕН иметь беззнаковый тип (диапазон 0 … 254 при числе параметров не более 255, п. 4.1.3); знаковый 8-битный тип не допускается. Признак отсутствия кодируется отдельно. `[U]` `(р.1.6)`

8.7.15. Контракт по идентификации параметров для внешних приложений: имя — единственный постоянный идентификатор; индекс — временный маркер текущей сессии обмена с данным узлом. Индексы идут подряд от 0 до `count − 1` без пропусков; порядок таблицы не является частью контракта и может изменяться между версиями прошивки. `[N]` `(р.1.6)`

8.7.16. Внешнее приложение ДОЛЖНО получать индексы в рамках сессии (запросом по имени либо перебором по возрастающим индексам до пустого имени), не сохранять их между сессиями и запрашивать заново после потери связи с узлом и после его перезапуска (приложение J). `[N]` `(р.1.6)`

8.7.17. Ответ `ExecuteOpcode` ДОЛЖЕН передавать в поле `argument` код причины при `ok = false`: 1 — запись запрещена режимом (Combat); 2 — сбой контрольного чтения Flash; 3 — запись заблокирована ожидающей перезагрузкой (п. 5.6.10); 4 — неизвестный код операции. При нескольких причинах применяется код, перечисленный первым в порядке проверки 4, 1, 3, 2. При `ok = true` поле `argument` повторяет значение из запроса и приложением не интерпретируется. Приложения, не читающие `argument`, ориентируются на `ok`. `[N]` `(р.1.8)`

8.7.18. Команды CLI, сохраняющие и сбрасывающие параметры, ДОЛЖНЫ использовать ту же службу отложенной перезагрузки (п. 5.6.12) и ту же блокировку записи; перезагрузка по команде CLI не зависит от `Config::CanTxEnable` и наличия шины CAN. `[N]` `(р.1.8)`

### 8.8. Диагностика EEPROM в BSP

8.8.1. При старте BSP выводит диагностику хранилища: адрес страницы, размер страницы, объём занятой области, результат аппаратной проверки по магическому числу. `[R]` `(р.1.1)`

8.8.2. Проверка магического числа в BSP ДОЛЖНА использовать константы подсистемы (`ParamConsts::EEPROM_MAGIC`, `ParamConsts::EEPROM_MAGIC_V1`) и НЕ ДОЛЖНА содержать собственной копии значения. Магия v1 в окне миграции сообщается как «формат v1, будет мигрирован», а не как ошибка. `[N]` `(р.1.1)`

8.8.3. Объём занятой области ДОЛЖЕН вычисляться как `12 + 32·N` (для образа v2) по фактическому числу слотов `N`; в формате v1 (по журналу: 1188 байт = `4 + 37·32`) величина оценивалась по общему числу параметров, а не по числу persistent-параметров. `[N]` `(р.1.1)`

8.8.4. Диагностика в BSP выполняется до инициализации реестра и НЕ ДОЛЖНА изменять содержимое страницы. `[R]` `(р.1.1)`

### 8.9. Зависимость от HAL CRC

8.9.1. Если применяется аппаратная реализация CRC (п. 6.6.4), модуль HAL CRC ДОЛЖЕН быть включён в конфигурации HAL проекта. `[N]` `(р.1.1)`

8.9.2. Тактирование блока CRC ДОЛЖНО включаться перед расчётом. `[N]` `(р.1.1)`

8.9.3. Если аппаратный CRC не включён в проекте либо выполнение происходит в QEMU (`Bsp_IsRunningInQemu()`), подсистема ДОЛЖНА использовать программную реализацию, не требуя модуля HAL CRC. `[N]` `(р.1.2)`

### 8.10. Драйвер нагрузки

8.10.1. Драйвер нагрузки (`PayloadDriver::init()`) вызывается после инициализации реестра, читает `sys.board_type` и выбирает драйвер нагрузки по типу платы. `[R]` `(р.1.2)`

8.10.2. Для `lts-5l-generic` (безопасный режим, аппаратные порты изолированы) и для неизвестного типа платы выбирается драйвер-заглушка с записью в журнал; неизвестное значение при штатной работе реестра недостижимо (п. 3.5.2), защитная ветка драйвера сохраняется. `[R]` `(р.1.2)`

8.10.3. Драйвер записывает `sys.payload_type` по п. 5.9.10; название нагрузки — информационное, только для отображения. `[R]` `(р.1.2)`

8.10.4. Название нагрузки — текст на русском языке в UTF-8 длиной не более 31 байта (п. 5.9.11). `[R]` `(р.1.2)`

## 9. Нефункциональные требования

### 9.1. Память

9.1.1. Хэш параметра НЕ ДОЛЖЕН дублироваться в RAM: при необходимости он читается из таблицы ROM по индексу. `[N]`

9.1.2. Потребление RAM реестром не ДОЛЖНО возрастать относительно формата v1. `[N]`

9.1.3. Временные буферы (слот 32 байта, строка 32 байта) ДОЛЖНЫ размещаться в стеке; динамическая память не используется. `[R]`

9.1.4. Таблица параметров ДОЛЖНА размещаться в ROM, не копироваться в RAM целиком. `[R]`

### 9.2. Быстродействие

9.2.1. Доступ по индексу — O(1); доступ к служебным параметрам из внутреннего кода — O(1) через compile-time индексы; доступ по имени — O(n) по числу параметров. `[U]`

9.2.2. Проверка образа и загрузка при старте СЛЕДУЕТ выполнять за время порядка 1 мс и менее (при любой реализации CRC). `[N]`

9.2.3. Вызов `save()` блокирует выполнение основного цикла на время `flush` (п. 8.1.3). Вызывающий код НЕ ДОЛЖЕН вызывать `save()` из обработчиков прерываний. Вызов допускается как на этапе конфигурирования при старте, так и в процессе работы (п. 2.1.3); потребители ДОЛЖНЫ допускать пропуск периодических задач на время операции (типично около 25 мс, граница — п. 9.2.4): минимальные периоды CAN-сообщений равны 5 мс (приложение A.2). `[R]` `(р.1.2)`

9.2.4. Длительность `save()` ДОЛЖНА быть существенно меньше таймаута сторожевого таймера `IWDG_TIMEOUT_MS = 2000` мс: верхняя граница — 200 мс (запас не менее десятикратного); подтверждается замером на оборудовании. `[R]` `(р.1.2)`

9.2.5. Задержка от запроса перезагрузки до сброса (не более `REBOOT_TX_DRAIN_TIMEOUT_MS + REBOOT_DELAY_MS` = 2500 мс плюс `FLUSH_DELAY_MS`) превышает `IWDG_TIMEOUT_MS` (2000 мс), поэтому ДОЛЖНА выполняться неблокирующе: отсчёт по `millis()` в тике службы (п. 5.6.12), а сторожевой таймер сбрасывается в каждой итерации цикла (`IWatchdog.reload()` в начале `loop()`). Блокирующей остаётся только пауза `FLUSH_DELAY_MS` (10 мс) после `Serial.flush()`. Сброс выполняет программная команда, а не сторожевой таймер (п. 5.6.11). `[R]` `(р.1.8)`

### 9.3. Надёжность

9.3.1. Подсистема НЕ ДОЛЖНА применять частично или полностью повреждённые данные образа (п. 7.5.2). `[N]`

9.3.2. CRC-32 обеспечивает обнаружение любой пачки ошибок длиной до 32 бит; вероятность необнаружения случайного искажения ориентировочно `2^-32`. `[N]`

9.3.3. Потеря питания во время записи страницы: подсистема ДОЛЖНА при следующем старте распознать неполный образ и перейти к заводским значениям. Сохранение прежних настроек в этом случае не гарантируется; текущее поведение (одна страница, без резервной копии) сохраняется решением заказчика, риск принят. Целостность конфигурации проверяет внешнее приложение; изменения параметров выполняются как правило при старте, но допускаются и в процессе работы (п. 2.1.3), риск принят с учётом этого. `[N]` `(р.1.2)`

9.3.4. Значения из хранилища ДОЛЖНЫ проходить проверку типа и допустимой области до применения. `[R]` `(р.1.1)`

9.3.5. Обращения за границы теневого буфера при загрузке ДОЛЖНЫ исключаться проверкой `count` до чтения слотов. `[N]`

### 9.4. Детерминизм

9.4.1. Одно и то же состояние реестра ДОЛЖНО порождать побайтово одинаковый образ (нулевое дополнение слотов, хвост `0xFF`, отсутствие неинициализированных байтов). `[N]`

### 9.5. Переносимость

9.5.1. Формат образа определён для little-endian. Перенос на big-endian платформу требует пересмотра п. 6.1.3. `[R]`

9.5.2. Код ДОЛЖЕН собираться gcc (arm-none-eabi) в режиме C++17 без расширений, не входящих в C++17. `[R]`

### 9.6. Износ Flash

9.6.1. Каждый `save()` с изменённым образом приводит к стиранию страницы; `save()` без изменений страницу не стирает (п. 5.4.9); частоту вызова ограничивает вызывающий код (п. 5.4.8, 9.2.3). `[R]` `(р.1.6)`

### 9.7. Параллелизм

9.7.1. Подсистема не содержит средств синхронизации. Все обращения выполняются из основного цикла `loop()` (CAN-обмен и CLI обслуживаются в нём же); вызовы из прерываний и иных контекстов ДОЛЖНЫ быть исключены либо сериализованы внешней блокировкой. `[R]` `(р.1.1)`

### 9.8. Сопровождаемость

9.8.1. Проверки инвариантов таблицы ДОЛЖНЫ выполняться компилятором (п. 4.5), а не в рантайме. `[N]`

9.8.2. Служебные параметры ДОЛЖНЫ адресоваться compile-time индексами; опечатка в имени — ошибка сборки. `[N]`

9.8.3. Каждое требование ДОЛЖНО быть прослеживаемо до кода и проверки (раздел 12). `[N]`

### 9.9. Использование CRC-периферии

Требования применяются, если выбрана аппаратная реализация CRC (п. 6.6.4).

9.9.1. Обращение к CRC-периферии ДОЛЖНО выполняться из основного цикла, не из прерываний. `[N]` `(р.1.1)`

9.9.2. Блок CRC — общий ресурс с контролем целостности прошивки; конфигурация по п. 6.6.5 совпадает с конфигурацией контроля целостности, поэтому расчёт образа EEPROM её не нарушает. Перед первым использованием ДОЛЖНО проверяться, что блок инициализирован (`HAL_CRC_Init`) с этой конфигурацией; если в других местах проекта применяется иная конфигурация, перед каждым расчётом ДОЛЖНА выполняться полная конфигурация. `[N]` `(р.1.2)`

9.9.3. Результат аппаратного расчёта используется без дополнительных преобразований (финального XOR и отражений нет). `[N]` `(р.1.2)`

9.9.4. Расчёт по частям (накопление) ДОЛЖЕН давать тот же результат, что расчёт за один проход. `[N]` `(р.1.1)`

9.9.5. Выбор аппаратной или программной реализации выполняется в одной точке (`computeCrc`) во время исполнения: по `Bsp_IsRunningInQemu()` и по наличию модуля HAL CRC. `[N]` `(р.1.2)`

## 10. Совместимость и эволюция

10.1. Обновление v1 → v2 ДОЛЖНО сохранять значения всех R/W-параметров, присутствовавших в v1 и имеющих в v2 то же имя, тот же тип и допустимое значение. `[N]`

10.2. Обновления между релизами формата v2 (добавление, удаление, перестановка параметров) ДОЛЖНЫ сохранять значения остальных параметров. `[N]`

10.3. Возврат прошивки с v2 на v1 не поддерживается: прошивка v1 сочтёт образ недействительным и применит заводские значения. Это ДОЛЖНО быть отражено в примечаниях к выпуску. `[N]`

10.4. Изменение раскладки страницы в будущем ДОЛЖНО сопровождаться новым магическим числом и, при необходимости, миграцией по аналогии с п. 7.4. `[N]`

10.5. Legacy-код миграции v1 (`ParamLegacyV1.h`, загрузчик, ветка магии `PARM`) ДОЛЖЕН быть удалён после обновления парка устройств; удаление оформляется новой ревизией документа. `[N]`

10.6. Выбор реализации CRC (программная или аппаратная) НЕ ДОЛЖЕН влиять на совместимость образов между релизами. `[N]` `(р.1.1)`

**Проверка таблицы параметров в CI.**

10.7. Проверка таблицы параметров ДОЛЖНА быть частью конвейера GitLab CI: отдельное задание, блокирующее слияние и выпуск при нарушении. Цель — не допустить случайного нарушения обмена между системами (имена параметров используются внешними приложениями) и потери сохранённых значений (п. 4.4.1). `[N]` `(р.1.5)`

10.8. В репозитории ДОЛЖЕН храниться манифест параметров — файл-контракт обмена. Для каждого параметра он ДОЛЖЕН содержать имя, тип и класс (R/W, RO, RAM-only), а также общее число параметров и числа по классам. СЛЕДУЕТ дополнительно записывать флаги, допустимую область и заводское значение для сведения. `[N]` `(р.1.5)`

10.9. Манифест ДОЛЖЕН формироваться автоматически из таблицы `defaultParamsList`, а не вестись вручную отдельно. При первой реализации допускается разбор `ParamDefaults.h`; число параметров СЛЕДУЕТ дополнительно контролировать независимым способом (например, хост-утилитой, собираемой из той же таблицы, или сравнением с `sys.param_count`). `[N]` `(р.1.5)`

10.10. Проверка ДОЛЖНА выполнять два сравнения: (а) таблица и манифест в одном коммите: имена, типы, классы и числа совпадают; (б) манифест и эталон выпущенной версии (манифест последнего релизного тега; СЛЕДУЕТ также целевой ветки). Сравнение (б) необходимо, так как удаление параметра вместе с правкой манифеста в одном изменении иначе не обнаруживается. `[N]` `(р.1.5)`

10.11. Правила сравнения: удаление или переименование параметра — ошибка; изменение типа или класса — ошибка; добавление параметра допустимо при обновлённом манифесте; изменение числа параметров без обновления манифеста — ошибка; изменение порядка параметров (индексов `GetSet`), флагов, допустимой области и заводского значения — предупреждение. `[N]` `(р.1.5)`

10.12. Осознанное удаление или изменение типа параметра допускается только по явной записи в файле изменений (имя параметра, причина, ссылка на согласование с владельцами внешних приложений) и подлежит ревью. Разрешение через флаг запуска задания НЕ ДОЛЖНО применяться. `[N]` `(р.1.5)`

10.13. Отчёт проверки ДОЛЖЕН содержать читаемый список различий (добавлено, удалено, изменено); при ошибках задание ДОЛЖНО завершаться с ненулевым кодом. `[N]` `(р.1.5)`

10.14. Выпускная сборка ДОЛЖНА выполняться полностью (без кэша объектных файлов) на билд-машине GitLab; CI ДОЛЖЕН проверять, что `sys.git_hash` не содержит суффикса `-dirty`. `[N]` `(р.1.5)`

## 13. Допущения и открытые вопросы

### 13.1. Допущения

13.1.1. Страница эмулируемой EEPROM принадлежит подсистеме целиком (п. 6.1.4, 8.1.6); иных потребителей страницы нет.

13.1.2. Ёмкость страницы: `E2END + 1 = 2048` (по журналу), число слотов 63.

13.1.3. Вызовы реестра выполняются из основного цикла (п. 9.7.1).

13.1.4. Число параметров (37 всего, 24 persistent) принято как исходное; после добавления `sys.git_hash` (RO) всего 38, persistent по-прежнему 24; полная таблица не предоставляется (п. 13.2.11). `(р.1.5)`

13.1.5. Способ применения изменённых значений потребителями (кроме двух параметров с флагом `REBOOT`) находится вне подсистемы; подсистема не уведомляет потребителей (п. 3.3.6). `(р.1.2)`

13.1.6. Все вычисляемые системные значения известны в момент применения заводских значений (приложение H). `(р.1.4)`

### 13.3. Примечания на будущее (информативно)

0          4        magic     0x50415232 ("PAR2")
4          4        crc32     по байтам [8 .. 12 + 32*N)
8          2        count     N
10         2        reserved  0
12         32       slot[0]
44         32       slot[1]
...        ...      ...
12+32*N    ...      0xFF до конца буфера (E2END + 1)

+0   4    hash   fnv1a32(name)
+4   1    tag    0 INT | 1 FLOAT | 2 BOOL | 3 STRING

Область CRC: от адреса 8 (`count`) до конца последнего слота; начало кратно 4, длина `4 + 32·N` кратна 4 (п. 6.6.3).

## Приложение G. Пример реализации расчёта CRC (информативно)

Примеры соответствуют п. 6.6.1 и 6.6.5. Векторы п. 6.6.8 получены эталонной программной реализацией; совпадение аппаратной реализации подтверждается тестом TC-36 на оборудовании.

### G.1. Программная реализация

```cpp
// Один шаг по 32-битному слову (п. 6.6.1): без отражений, без финального XOR.
inline uint32_t crcStepWord( uint32_t crc, uint32_t word )
{
    crc ^= word;
    for ( int i = 0; i < 32; ++i ) crc = ( crc & 0x80000000u ) ? ( crc << 1 ) ^ 0x04C11DB7u : ( crc << 1 );
    return crc;
}

// Слово little-endian из 4 байт теневого буфера.
inline uint32_t readWordLe( uint32_t a )
{
    return  static_cast<uint32_t>( eeprom_buffered_read_byte( a ) )
         | (static_cast<uint32_t>( eeprom_buffered_read_byte( a + 1 ) ) << 8 )
         | (static_cast<uint32_t>( eeprom_buffered_read_byte( a + 2 ) ) << 16 )
         | (static_cast<uint32_t>( eeprom_buffered_read_byte( a + 3 ) ) << 24 );
}

// [from, to): from и to - from кратны 4 (п. 6.6.3).
uint32_t computeCrcSw( uint32_t from, uint32_t to )
{
    uint32_t crc = 0xFFFFFFFFu;
    for ( uint32_t a = from; a < to; a += 4 ) crc = crcStepWord( crc, readWordLe( a ) );
    return crc;
}
```

Область до 2 КБ — порядка 500 слов; время расчёта по порядку величины десятые доли миллисекунды при 170 МГц (не измерялось).

### G.2. Аппаратная реализация (опционально)

```cpp
// Конфигурация — та же, что в контроле целостности прошивки.
hcrc.Instance                     = CRC;
hcrc.Init.DefaultPolynomialUse    = DEFAULT_POLYNOMIAL_ENABLE;
hcrc.Init.DefaultInitValueUse     = DEFAULT_INIT_VALUE_ENABLE;
hcrc.Init.InputDataInversionMode  = CRC_INPUTDATA_INVERSION_NONE;
hcrc.Init.OutputDataInversionMode = CRC_OUTPUTDATA_INVERSION_DISABLE;
hcrc.InputDataFormat              = CRC_INPUTDATA_FORMAT_WORDS;
// HAL_CRC_Init( &hcrc ) вызывается один раз (см. п. 9.9.2).

uint32_t computeCrcHw( uint32_t from, uint32_t to )
{
    uint32_t words[16];
    uint32_t crc   = 0;
    bool     first = true;

    for ( uint32_t a = from; a < to; )
    {
        uint32_t n = 0;
        for ( ; n < 16 && a < to; ++n, a += 4 ) words[n] = readWordLe( a );

        // Первая порция сбрасывает регистр, остальные накапливают результат.
        crc   = first ? HAL_CRC_Calculate( &hcrc, words, n ) : HAL_CRC_Accumulate( &hcrc, words, n );
        first = false;
    }

    return crc;   // без XOR и отражений
}

uint32_t computeCrc( uint32_t from, uint32_t to )
{
#if defined( HAL_CRC_MODULE_ENABLED )
    if ( !Bsp_IsRunningInQemu() && crcHwReady() ) return computeCrcHw( from, to );   // crcHwReady() — инициализация HAL_CRC_Init
#endif
    return computeCrcSw( from, to );
}
```

### G.3. Замечания

- Пословный расчёт эквивалентен побайтовому CRC-32/MPEG-2 (полином `0x04C11DB7`, начальное значение `0xFFFFFFFF`, без отражений и XOR), если байты каждой четырёхбайтной группы подавать в обратном порядке: старший байт слова идёт первым. Эквивалентность проверена вычислением.
- CRC-32/ISO-HDLC (`etl::crc32`, `zlib.crc32`) даёт другое значение для тех же данных и для образа EEPROM не применяется.

## Приложение H. Доступность значений системных параметров при `applyDefaults()`

Информативное приложение. Цель — проверить, какие вычисляемые системные значения известны в момент вызова `applyDefaults()` (из `init()` и `resetToDefaults()`), и обосновать п. 5.9.5.

В формате v1 `refreshSysParams()` вызывается при каждом `getByIndex`, при успешном `getByName` и в `print()` и присваивает пять параметров. В таблице для трёх из них стоят значения-заглушки (`sys.param_count` = 0, `sys.stamp` = 0, `sys.uid` = `""`); `sys.fw_ver` и `sys.is_debug` уже вычислены в таблице.

| Параметр | Заглушка в таблице | Источник значения | Известен при `applyDefaults()` | Основание |
| :--- | :--- | :--- | :---: | :--- |
| `sys.param_count` | `0` | `PARAM_COUNT` | да | константа компиляции |
| `sys.fw_ver` | `SemanticVersion(MAJOR, MINOR, PATCH).raw` | `MAJOR`, `MINOR`, `PATCH` | да | константа компиляции, значение уже в таблице |
| `sys.stamp` | `0` | `BUILD_STAMP` (`version.h`) | да | макрос от `__DATE__`/`__TIME__` — константа компиляции; присваивается в `ParamRegistry.cpp` (п. 4.4.4) |
| `sys.is_debug` | `Config::DebugSensors` | `Config::DebugSensors` | да | константа компиляции, значение уже в таблице |
| `sys.uid` | `""` | регистры `UID_BASE` и `Bsp_IsRunningInQemu()` | да | только регистры MCU: `Bsp_IsRunningInQemu()` читает `DBGMCU->IDCODE` (п. 8.2.2) |
| `sys.payload_type` (вне вычисляемых) | `""` | `PayloadDriver::init()` | нет | значение выставляется после инициализации реестра; `refreshSysParams()` его не изменяет; `applyDefaults()` в составе `resetToDefaults()` очищает значение до следующего старта |

### H.1. Проверка `BUILD_STAMP`

По коду `version.h` и пробной компиляции (gcc 13.3, C++17):

- Формат: `(ГГГГММДД) × 1000000 + ЧЧММСС`, тип `uint64_t`; например `20260919183241`. Превышает `int32`, помещается в `int64`; в `print()` выводится по ветви разбиения (п. 5.7.3).
- Допустим в constant expression: `static_assert` и инициализатор `inline constexpr` массива компилируются.
- Значение различается между единицами трансляции: две единицы, скомпилированные с интервалом в 2 секунды, дали `20260920224610` и `20260920224612`. Поэтому в таблицу заголовка (`inline constexpr`, включаемую в разные единицы) значение помещать нельзя: нарушение ODR, итог определяется выбором компоновщика.
- `sys.stamp` отражает момент компиляции `ParamRegistry.cpp`; при инкрементальной сборке он может отставать от момента сборки прошивки и отличаться от `FirmwareMeta` (строка `Stamp` журнала): п. 5.9.12; выпускная сборка полная, на билд-машине (п. 10.14).

### H.2. Вывод

1. Все вычисляемые значения известны в момент `applyDefaults()`. Поэтому они вычисляются один раз в конце `applyDefaults()`, а чтение их не пересчитывает (п. 5.2.4, 5.9.5).
2. `BUILD_STAMP` присваивается только в `ParamRegistry.cpp`, в таблицу заголовка он не помещается (п. 4.4.4).
3. Обновление в геттерах (ревизии 1.2 и 1.3) отменено; `params_` снова не `mutable`.
4. Условия применимости: `applyDefaults()` вызывается только из `init()` и `resetToDefaults()`; порядок инициализации BSP не влияет (п. 8.2.2).

## Приложение I. Пример проверки таблицы параметров в CI (информативно)

Пример иллюстрирует п. 10.7–10.14 и 5.9.13–5.9.16. Пути и имена файлов условные. Скрипт запущен на предоставленном фрагменте `ParamDefaults.h` (извлечено 10 параметров) по сценариям из I.5. Логика выбора эталонного тега проверена в тестовом репозитории (ветка, тег, первый тег); задание GitLab CI целиком и фрагмент CMake — эскизы, на вашем конвейере не проверялись. Проверка длины RO-строк и значения `unknown` по умолчанию проверены пробной компиляцией (gcc 13.3, C++17).

 "params": [

### I.2. Правила проверки

| Ситуация | Результат |
| :--- | :---: |
| Таблица и манифест в одном коммите различаются (имя, тип, класс, число) | ошибка |

| Изменён порядок параметров | предупреждение |

### I.3. Скрипт `tools/params_manifest.py`

```python
#!/usr/bin/env python3
"""Проверка таблицы параметров в CI (ТЗ 10.7-10.14).

  export : разобрать ParamDefaults.h и записать манифест (JSON).
  check  : сравнить таблицу с манифестом (10.10а) и манифест с эталоном релиза (10.10б).

Код возврата: 0 - проверка пройдена (возможны предупреждения), 1 - есть ошибки.
"""
import argparse
import json
import re
import sys

# построитель -> (тип, класс)
KIND = {
    "p_int": ("int", "rw"), "p_float": ("float", "rw"),
    "p_bool": ("bool", "rw"), "p_string": ("string", "rw"),
    "p_ram_bool": ("bool", "ram"),
    "p_ro_int": ("int", "ro"), "p_ro_float": ("float", "ro"),
    "p_ro_bool": ("bool", "ro"), "p_ro_string": ("string", "ro"),
}
CALL = re.compile(r'ParamInit::(p_[a-z_]+)\s*\(\s*"([^"]+)"')


def strip_comments(text):
    text = re.sub(r"/\*.*?\*/", "", text, flags=re.S)
    return re.sub(r"//[^\n]*", "", text)


def extract(header_path):
    text = strip_comments(open(header_path, encoding="utf-8").read())
    params = []
    for m in CALL.finditer(text):
        builder, name = m.group(1), m.group(2)
        if builder not in KIND:
            sys.exit(f"ОШИБКА: неизвестный построитель {builder} для параметра '{name}'")
        ptype, pclass = KIND[builder]
        params.append({"name": name, "type": ptype, "class": pclass})
    return params


def build_manifest(params):
    classes = [p["class"] for p in params]
    return {
        "format": 1,
        "counts": {"total": len(params), "rw": classes.count("rw"),
                   "ro": classes.count("ro"), "ram": classes.count("ram")},
        "params": params,
    }


def load_json(path):
    with open(path, encoding="utf-8") as f:
        return json.load(f)


def sig(p):
    return (p["type"], p["class"])


def check(current, manifest, baseline, changes):
    errors, warnings = [], []
    names = [p["name"] for p in current]
    for n in sorted({n for n in names if names.count(n) > 1}):
        errors.append(f"[таблица] имя '{n}' встречается более одного раза")
    cur = {p["name"]: p for p in current}
    man = {p["name"]: p for p in manifest["params"]}

    # (а) таблица <-> манифест в том же коммите
    for n in sorted(set(cur) - set(man)):
        errors.append(f"[манифест] параметр '{n}' есть в таблице, но не в манифесте: обновите манифест")
    for n in sorted(set(man) - set(cur)):
        errors.append(f"[манифест] параметр '{n}' есть в манифесте, но не в таблице")
    for n in sorted(set(cur) & set(man)):
        if sig(cur[n]) != sig(man[n]):
            errors.append(f"[манифест] '{n}': в таблице {sig(cur[n])}, в манифесте {sig(man[n])}")
    expected = build_manifest(current)["counts"]
    if manifest.get("counts") != expected:
        errors.append(f"[манифест] числа параметров {manifest.get('counts')} не совпадают с фактическими {expected}")

    # (б) манифест <-> эталон выпущенной версии
    if baseline is not None:
        base = {p["name"]: p for p in baseline["params"]}
        ok_removed = set(changes.get("removed", []))
        ok_type = set(changes.get("type_changed", []))
        for n in sorted(set(base) - set(man)):
            if n not in ok_removed:
                errors.append(f"[эталон] параметр '{n}' удалён или переименован без записи в файле изменений")
        for n in sorted(set(base) & set(man)):
            if sig(base[n]) != sig(man[n]) and n not in ok_type:
                errors.append(f"[эталон] '{n}': тип или класс изменён {sig(base[n])} -> {sig(man[n])} без записи в файле изменений")
        common_base = [p["name"] for p in baseline["params"] if p["name"] in man]
        common_man = [p["name"] for p in manifest["params"] if p["name"] in base]
        if common_base != common_man:
            warnings.append("[эталон] изменён порядок параметров (меняются индексы GetSet)")
        added = sorted(set(man) - set(base))
        if added:
            warnings.append("[эталон] добавлены параметры: " + ", ".join(added))
    return errors, warnings


def main():
    ap = argparse.ArgumentParser(description=__doc__, formatter_class=argparse.RawDescriptionHelpFormatter)
    sub = ap.add_subparsers(dest="cmd", required=True)
    e = sub.add_parser("export")
    e.add_argument("--header", required=True)
    e.add_argument("--out", required=True)
    c = sub.add_parser("check")
    c.add_argument("--header", required=True)
    c.add_argument("--manifest", required=True)
    c.add_argument("--baseline")
    c.add_argument("--changes")
    a = ap.parse_args()

    current = extract(a.header)
    if a.cmd == "export":
        with open(a.out, "w", encoding="utf-8") as f:
            json.dump(build_manifest(current), f, ensure_ascii=False, indent=1)
            f.write("\n")
        print(f"Манифест записан: {len(current)} параметров")
        return 0

    manifest = load_json(a.manifest)
    baseline = load_json(a.baseline) if a.baseline else None
    changes = load_json(a.changes) if a.changes else {}
    errors, warnings = check(current, manifest, baseline, changes)
    for w in warnings:
        print("ПРЕДУПРЕЖДЕНИЕ:", w)
    for er in errors:
        print("ОШИБКА:", er)
    print(f"Параметров в таблице: {len(current)}; ошибок: {len(errors)}; предупреждений: {len(warnings)}")
    return 1 if errors else 0


if __name__ == "__main__":
    sys.exit(main())
```

Ограничения примера: разбор регулярными выражениями находит только вызовы вида `ParamInit::p_*( "имя"` и не поддерживает параметры, созданные другими средствами; закомментированные вызовы игнорируются. Независимый контроль числа параметров (п. 10.9) в примере не реализован.

## Приложение J. Контракт обмена с внешним приложением (информативно)

Основано на описании ROS-ноды `lts_control` и тестовых скриптах чтения, записи и проверки связи (`read_single_param.py`, `write_single_param.py`, `lts_ping.py`).

### J.1. Принципы

1. Имя параметра — единственный постоянный идентификатор.
2. Индекс — временный маркер сессии; нигде не сохраняется; используется только для экономии трафика (имя в запросе увеличивает число CAN-кадров).
3. Прошивка отвечает на каждый запрос; отсутствие результата выражается пустым ответом.
4. Прошивка всегда возвращает фактическое значение после попытки записи; приложение определяет принятие записи сравнением с запрошенным.
5. Запись параметров сама не перезагружает плату; сохранение и перезагрузка выполняются командой SAVE.

### J.2. Штатная ROS-нода: целевая синхронизация по именам

Нода не вычитывает всю таблицу. Словарь параметров (обычно не более 10) задан в launch-файле. Конечный автомат нода выполняет последовательно для каждого параметра очереди:

1. Читает параметр запросом `GetSet` с именем и пустым значением.
2. Сравнивает возвращённое значение с заданным.
3. Если значения совпали, параметр пропускается (экономия трафика).
4. Если значения различаются, записывает запросом с именем и значением; принятие определяет по возвращённому значению; отказ (RO, вне диапазона) фиксируется в журнале, синхронизация продолжается.
5. Если хотя бы одна запись прошла, поднимает флаг и по окончании очереди отправляет `ExecuteOpcode` (SAVE).

Порядок очереди (параметры с перезагрузкой — в конец) — осторожность прежней логики. Поскольку прошивка перезагружается только по SAVE (п. 5.6.4, 5.6.9), порядок записи значения не имеет; в новых версиях планируется записывать параметры в любом порядке, а перезагрузку инициировать прошивкой по команде SAVE, если изменён параметр с флагом `REBOOT`.

### J.3. Тестовые скрипты

| Скрипт | Поведение | Требования к прошивке |
| :--- | :--- | :--- |
| `read_single_param.py` | Чтение по имени, три попытки, сравнение имени в ответе с запрошенным; пустое имя в ответе означает «параметр не существует» | 8.7.11: пустой ответ на неизвестное имя |
| `write_single_param.py` | Перебор индексов 0 … 255 до совпадения имени, пустого имени или таймаута 1 с; запись по индексу с пустым именем (запрос короче, два CAN-кадра); сравнение запрошенного и возвращённого значений; SAVE | 8.7.6, 8.7.11, 8.7.14, 8.7.15 |
| `lts_ping.py` | Приём `NodeStatus` и сообщений датчиков и нагрузки без отправки запросов | Вне подсистемы параметров |

### J.4. Следствия для прошивки

| Наблюдение | Следствие | Пункт |
| :--- | :--- | :---: |
| Приложение при каждом старте сравнивает и записывает `float`: значение Python (двойная точность) может не совпасть с `float32` платы | Повторные SAVE не должны изнашивать Flash | 5.4.9 |
| Перебор индексов завершается по пустому имени или по таймауту; без ответа каждый запрос ждёт таймаут | Пустой ответ на любой запрос без результата | 8.7.11 |
| Запись по индексу выполняется без проверки имени до применения; таблица может измениться между перебором и записью | Индексы сессионные; перебор заново после потери связи и перезапуска | 8.7.15, 8.7.16 |
| Скрипт записи обрезает строки до 31 символа со ссылкой на DSDL | Реальные пределы задаёт прошивка: 31 байт в RAM, 27 для сохраняемых; лимит DSDL больше | 3.1.4, 3.1.5 |
| `ExecuteOpcode` может вернуть `ok = false` (например, запрет записи в режиме Combat) | Режимы вне ТЗ; ответ приходит всегда | 2.4.2, 8.7.7 |
| `ok = false` при запрете записи, сбое Flash, блокировке перед сбросом и неизвестной операции неразличимы для приложения | Коды причины 1–4 в поле `argument` ответа | 8.7.17 |

### J.5. Рекомендации приложению

- Определять перезапуск узла по уменьшению `uptime_sec` в `NodeStatus` и сбрасывать карту индексов вместе с потерей связи.
- Перед записью по индексу сверять имя в ответе на последнее чтение того же индекса; при несовпадении перебирать заново.
- Сравнивать `float` с допуском, соответствующим `float32`, чтобы не записывать неизменившиеся значения.
- Интерпретировать `argument` ответа `ExecuteOpcode` только при `ok = false`; после успешного SAVE не отправлять `GetSet` с записью до перезапуска узла: запись отклоняется (п. 5.6.10).
