Содержание:

1. Заголовок и реквизиты
2. История ревизий
3. Изменения ревизии X.Y
4. Содержание

6. Раздел 2. Общее описание
7. Предметные разделы
8. Функциональные требования: жизненный цикл и API
9. Требования к интерфейсам
10. Нефункциональные требования
11. Совместимость и эволюция
12. Верификация
13. Матрица прослеживаемости
14. Допущения и открытые вопросы
15. Приложения

Примеры в блоках кода — фрагменты образца (подсистема параметров во Flash-эмуляции EEPROM, STM32G474). Бери из них форму, а не содержание.

## 1. Заголовок и реквизиты

```markdown
# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## <Полное название модуля/подсистемы> (<платформа>)

| Реквизит | Значение |
| :--- | :--- |
| **Документ** | TECHNICAL_SPECIFICATION_<МОДУЛЬ>.md |
| **Ревизия** | 1.0 (черновик для согласования) |
| **Дата формирования** | ДД.ММ.ГГГГ |
| **Метод формирования** | <с нуля / обратная разработка по коду X, журналу Y / приведение к целевой реализации Z> |
| **Целевая платформа** | <МК>, <компилятор и версия>, <язык и стандарт>, <система сборки>, <фреймворки и библиотеки с версиями> |
| **Связанные документы** | «<План/архитектура, редакция N>» |
| **Связанные файлы кода** | `File1.h`, `File1.cpp` |
```

Правила:

- Заголовок первого уровня — всегда «ТЕХНИЧЕСКОЕ ЗАДАНИЕ»; название модуля — заголовок второго уровня. Название говорит, что делает модуль, а не как называется класс: «Подсистема хранения и управления параметрами во Flash-эмуляции EEPROM», а не «ParamRegistry».
- Версии инструментов указываются точно: от них зависят требования (например, отсутствие `%lld` в newlib-nano, отключённые исключения в ETL).
- «Метод формирования» кратко перечисляет источники. Если ревизия опирается на новые источники, они добавляются сюда и в п. 1.3.
- Строки, не относящиеся к модулю, можно опустить (например, «Связанные файлы кода» для документа до начала реализации), но порядок оставшихся не меняется.

## 2. История ревизий

```markdown
### История ревизий

| Ревизия | Дата | Описание |
| :---: | :---: | :--- |
| 1.0 | 21.09.2026 | Первая редакция. Требования восстановлены по коду v1 и согласованы с реализацией формата v2. |
| 1.1 | 21.09.2026 | Учтены ответы заказчика и журнал загрузки: …; закрыты вопросы 13.2.1–13.2.4. |
```

- Порядок строк — по возрастанию ревизий (новейшая внизу): историю читают как летопись.
- Описание сообщает суть: что учтено (источник), что решено, что добавлено, какие вопросы закрыты или остаются открытыми. Не пересказывай таблицу изменений целиком.
- Если ревизия отменяет решение предыдущей, это пишется прямо: «обновление в геттерах (ревизия 1.2) отменено».

## 3. Изменения ревизии X.Y

```markdown
### Изменения ревизии 1.2

Изменённые и новые пункты ревизии 1.2 помечены `(р.1.2)`.

| Пункты | Тип | Суть |
| :--- | :---: | :--- |
| 3.1.6, 3.1.7 | нов. | Длины строк в байтах (UTF-8); RO-строки могут содержать кириллицу |
| 6.6.1, 6.6.4 | изм. | CRC — слово-ориентированный вариант блока CRC STM32 |
| 11.2 | изм./нов. | TC-30 изменён; TC-45 … TC-49 |
| 12, 13 | изм. | Матрица обновлена; вопросы ревизии 1.1 закрыты |
| Приложение H | нов. | Доступность системных параметров при `applyDefaults()` |
```

- Блок на каждую ревизию начиная с 1.1; блоки идут от новейшего к старейшему, сразу после истории ревизий.
- В самом раннем блоке (ревизии 1.1) один раз даётся легенда: «Обозначения: **нов.** — новое требование, **изм.** — изменённый текст при сохранении номера, **искл.** — исключённое требование.»
- Строки группируют соседние пункты одного смысла; строки идут в порядке номеров пунктов; разделы 11–13 и приложения — в конце таблицы.
- Если блоков становится очень много (больше 8–10), старые блоки можно перенести в приложение «Журнал изменений ревизий» с сохранением содержимого; в начале документа остаются последние 2–3 блока и ссылка на приложение.

## 4. Содержание

```markdown
## Содержание

1. Введение
2. Общее описание
3. <Предметный раздел>
…
13. Допущения и открытые вопросы
- Приложение A. <Название>
- Приложение B. Сводка констант
```

- Разделы — нумерованным списком без ссылок (номера совпадают с номерами разделов), приложения — маркированным списком с полным названием, включая пометку «(информативно)».
- Содержание обновляется при добавлении раздела или приложения; это отмечается в таблице изменений ревизии.

## 5. Раздел 1. Введение

Типовые подразделы:

| Подраздел | Что пишется |
| :--- | :--- |
| 1.1. Назначение документа | Что определяет документ; что каждое требование имеет номер для ссылок из кода, тестов и матрицы |
| 1.2. Область применения | К каким модулям/файлам применимо; что явно не описывается и где описаны требования к взаимодействию |
| 1.3. Метод формирования | Источники; что считается целевой реализацией; правило разрешения расхождений «документ ↔ код»; источники каждой ревизии |
| 1.4. Термины и сокращения | Таблица `Термин | Определение` |
| 1.5. Связанные документы и нормативные ссылки | Планы, стандарты, спецификации протоколов, алгоритмы (со ссылкой на пункт, где заданы параметры) |
| 1.6. Соглашения документа | Модальность, нумерация, маркеры, нормативность разделов, ссылки из кода, правила ревизий |

### 1.3 — правило расхождений

Обязательная формулировка (адаптируй):

```markdown
1.3.3. Целевой реализацией считается <…>. В случае расхождения между этим документом и кодом расхождение считается дефектом одного из них и разрешается пересмотром ревизии документа. Известные расхождения перечислены в приложении F.
```

### 1.4 — термины

- Определяй каждый термин, который используется в требованиях в узком смысле («Слот», «Образ», «Допустимая область»). Если определение уточнялось в ревизии — пометка `(р.X.Y)` в конце определения.
- Определение — одна-две фразы; ссылки на пункты допустимы.

### 1.6 — соглашения документа

Минимальный состав (подставь номера разделов своего документа):

```markdown
1.6.1. Модальность: **ДОЛЖНА / ДОЛЖЕН** — обязательное требование; **СЛЕДУЕТ** — рекомендуемое; **МОЖЕТ** — допустимое.

1.6.2. Нумерация: каждый пункт имеет номер вида `X.Y.Z`. Номер требования не переиспользуется; исключённое требование остаётся в тексте с пометкой «(исключено)».

1.6.3. Маркеры происхождения в конце требований:

| Маркер | Значение |
| :---: | :--- |
| **[R]** | Восстановлено из существующего кода, поведение сохраняется. |
| **[N]** | Новое требование. |
| **[U]** | Уточнение или исправление относительно существующего кода. |

1.6.4. Разделы 1–2 и приложения — информативные; разделы 3–11 — нормативные.

1.6.5. Ссылки на пункты ТЗ из кода оформляются по приложению D.

1.6.6. Правила ведения документа: …
```

Правила ведения документа (п. 1.6.6 или отдельный подраздел 1.7 при большом объёме) перечисляют: формат номера ревизии и статусы; пометку `(р.X.Y)`; ведение истории и блоков изменений; обязательные обновления смежных разделов при каждой ревизии; порядок закрытия вопросов. Формулировки — в SKILL.md, раздел «Правила ведения документа и ревизий».

## 6. Раздел 2. Общее описание

Раздел информативный, но пункты нумеруются так же (на них тоже ссылаются). Маркеры ставятся, если пункт фиксирует поведение.

| Подраздел | Что пишется |
| :--- | :--- |
| 2.1. Контекст | Где работает модуль, кто к нему обращается, как он используется в жизненном цикле устройства (конфигурирование при старте, работа, обновление) |
| 2.2. Функции | Перечень функций — по пункту на функцию, одной фразой |
| 2.3. Роли и потребители | Таблица `Роль | Взаимодействие`: прикладной код, CLI, протоколы, BSP, внешние приложения, разработчик, CI |
| 2.4. Границы | Что вне области ТЗ и почему (решение заказчика, другой модуль) |
| 2.5. Ограничения платформы | Язык и стандарт, компилятор, порядок байтов, куча, библиотеки, профиль сборки (исключения, RTTI), версии |

Совет: ограничения платформы (2.5) — источник многих неочевидных требований; ссылайся на них из разделов 5 и 9 («недопустимо, п. 2.5.5»).

## 7. Предметные разделы

Вставляются между разделами 2 и «Функциональными требованиями» и описывают предмет модуля независимо от API. Типовые варианты для встраиваемых систем:

| Модуль | Возможные предметные разделы |
| :--- | :--- |
| Хранение параметров, файловые структуры | Модель параметра; таблица времени проектирования; формат хранения (нормативный); алгоритмы (нормативные) |
| Драйвер периферии | Модель устройства и регистров; режимы работы; конечный автомат; тайминги |
| Протокол обмена | Модель сообщений; кодирование кадров; конечный автомат сеанса; обработка ошибок |
| Загрузчик | Раскладка памяти; формат образа; алгоритм обновления; проверка целостности |
| Регулятор, обработка сигналов | Модель объекта; алгоритм; параметры настройки; ограничения и насыщения |

Правила:

- Форматы и алгоритмы, от которых зависит совместимость, помечай в заголовке «(нормативный)» / «(нормативные)».
- Раскладки — таблицей `Смещение | Размер | Поле | Значение`; дублируй схемой в приложении.
- Алгоритм — упорядоченными шагами «(а) … (б) …» в одном пункте либо пунктом на шаг; нештатные состояния — таблицей `Состояние | Действие | Статус | …` плюс пункт «Поведение ДОЛЖНО соответствовать таблице».
- Проверки времени компиляции (`static_assert`) выделяй в подраздел: «Нарушение любого из условий ДОЛЖНО приводить к ошибке компиляции:» и далее по пункту на условие.

## 8. Функциональные требования: жизненный цикл и API

Заголовок раздела: «Функциональные требования: жизненный цикл и API». Подразделы следуют жизненному циклу модуля, по подразделу на операцию или группу операций, с именем операции в заголовке:

```markdown
### 5.1. Инициализация (`init`)
### 5.2. Чтение
### 5.3. Запись значения (`setValue`)
### 5.4. Сохранение (`save`)
### 5.5. Сброс к заводским значениям (`resetToDefaults`)
### 5.6. Запрос перезагрузки
### 5.7. Диагностика
```

Для каждой операции опиши:

1. **Предусловия и порядок вызова** — когда вызывается, сколько раз, что должно предшествовать («`init` ДОЛЖЕН вызываться единожды до любого другого обращения»).
2. **Шаги** — если порядок важен, строго по порядку: «ДОЛЖЕН выполнять шаги строго в следующем порядке: (а) … (б) …».
3. **Ветвления по состоянию** — пункт на ветку: условие → действия → статус → побочные эффекты (пишет ли во Flash).
4. **Входные значения** — проверка диапазона, приведение типов (таблица правил), обработка недопустимых.
5. **Результат и ошибки** — возвращаемое значение для каждого случая; «При возврате `false` значение НЕ ДОЛЖНО изменяться».
6. **Побочные эффекты и запреты** — что операция не должна делать («не обращается к хранилищу», «не изменяет значения в RAM»).
7. **Сложность и блокировки** — O(1)/O(n), блокирующая ли, можно ли из прерывания (или ссылка на раздел 9).
8. **Журнал** — какие события фиксируются.

Удобные формы:

- Таблица правил приведения/аксессоров `Аксессор | INT | FLOAT | …`.
- Для последовательностей с участием нескольких модулей (сохранение → ответ → выдержка → сброс) — один пункт с перечислением шагов и отдельные пункты на поведение при неуспехе.
- Статусы/коды возврата — перечислением в одном пункте с последующими ссылками.

## 9. Требования к интерфейсам

Подраздел на каждый внешний интерфейс модуля: то, что модуль использует, и то, кто использует модуль.

| Подраздел | Что фиксируется |
| :--- | :--- |
| Драйвер (Flash, шина, периферия) | Перечень используемых операций, их семантика, длительность, блокирующие ли; адреса и размеры; ошибка компиляции при отсутствии конфигурации |
| BSP | Сигнатуры функций, кодировка аргументов, от чего зависит результат, можно ли вызывать на любом этапе |
| Журнал | Функция вывода, ограничения форматирования |
| Сторожевой таймер | Когда сбрасывается |
| Информация о сборке | Используемые константы и определения системы сборки |
| Библиотеки (HAL, ETL, …) | Версии, используемые компоненты, неподходящие альтернативы |
| Внешние потребители и протоколы | API, используемый потребителями; сервисы протокола; соответствие типов; поведение при отказе; обязательность ответа; коды причин |

Правила:

- Контракт с внешним приложением формулируй с обеих сторон: что гарантирует прошивка и что ДОЛЖНО делать приложение. Подробный разбор существующих клиентов — в информативное приложение.
- Если модуль не использует интерфейс напрямую, но зависит от его поведения (например, драйвер нагрузки пишет в RO-параметр), это тоже фиксируется как контракт.

## 10. Нефункциональные требования

Типовые подразделы для встраиваемых систем (используй применимые, порядок сохраняй):

| Подраздел | Примеры требований |
| :--- | :--- |
| Память | Нет кучи; буферы в стеке с размерами; таблицы в ROM; бюджет RAM/ROM или «не возрастает относительно v1» |
| Быстродействие | Сложность операций; граница длительности с запасом относительно WDT; запрет вызова из ISR; влияние на периодические задачи |
| Надёжность | Поведение при повреждении данных; вероятность необнаружения ошибки; потеря питания; принятые риски (с указанием, что риск принят заказчиком) |
| Детерминизм | Одинаковое состояние → побайтово одинаковый образ; отсутствие неинициализированных байтов |
| Переносимость | Порядок байтов; стандарт языка без расширений |
| Износ | Число стираний; отсутствие записи без изменений |
| Параллелизм | Контекст вызовов (основной цикл, RTOS-задача, ISR); средства синхронизации |
| Сопровождаемость | Проверки при компиляции вместо рантайма; прослеживаемость |
| Использование периферии | Общие ресурсы (CRC, DMA, таймеры), конфигурация, конфликты |

Каждое требование содержит числовую границу или проверяемое условие и метод подтверждения («подтверждается замером на оборудовании»).

## 11. Совместимость и эволюция

Необязательный раздел; нужен, если у модуля есть хранимые данные, протокол или внешние клиенты. Пункты двухуровневые (`10.1`, `10.2`), допустимы жирные подзаголовки внутри раздела.

Что фиксируется: обновление со старой версии (что сохраняется); обновления между релизами; откат (поддерживается ли, что указать в примечаниях к выпуску); будущие изменения формата (новая магия, миграция); удаление legacy-кода (условие и оформление ревизией); контроль контракта в CI (манифест, правила сравнения, ошибки и предупреждения, порядок осознанного изменения).

## 12. Верификация

```markdown
### 11.1. Методы

| Обозначение | Метод |
| :---: | :--- |
| A | Анализ / проверка на этапе компиляции (`static_assert`, ошибка сборки) |
| T | Тестирование (модульные тесты на хосте или в эмуляторе с подменой драйвера) |
| I | Инспекция кода и документации |
| D | Демонстрация на оборудовании |

### 11.2. Тест-кейсы

| TC | Сценарий | Ожидаемый результат |
| :---: | :--- | :--- |
| TC-01 | Пустой образ (`0xFF`) | Заводские значения, `DefaultsEmpty`, страница валидна |
```

Правила:

- Тест-кейс — одна строка: сценарий (исходное состояние и действие) и наблюдаемый ожидаемый результат (значения, статусы, число вызовов мока, ошибка компиляции). Если в одной строке несколько вариантов, результаты перечисляются через «;» в том же порядке.
- Для каждой ветки ошибок и каждого нештатного состояния — свой тест-кейс.
- Контрольные значения (CRC, хэши) в тест-кейсах берутся из нормативного пункта с векторами.
- Если нумерация согласована с внешним планом (например, TC-01…TC-18 из плана рефакторинга), это указывается фразой перед таблицей.
- Изменённый в ревизии тест-кейс помечается в столбце сценария или результата `(р.X.Y)` либо перечисляется в таблице изменений ревизии.

## 13. Матрица прослеживаемости

```markdown
## 12. Матрица прослеживаемости

Условные обозначения файлов: **PD** — `ParamDefaults.h`; **PH** — `ParamRegistry.h`; **PC** — `ParamRegistry.cpp`.

Пометка **⚠** — реализация отсутствует или отличается, необходима доработка (приложение F).

### 12.1. Модель и таблица (разделы 3–4)

| Требования | Реализация | Проверка |
| :--- | :--- | :--- |
| 3.1.1, 3.1.2 | PD: `ParamType`; PH: `ParamValue` | TC-02, TC-06 (T, I) |
| 3.4.6 ⚠ | PD: `validateTable` (проверка длины имени) | TC-39 |
| 4.1.3 | PD: `PARAM_COUNT_AUTO` (`uint8_t`) | A |
```

Правила:

- Легенда сокращений файлов и пометки ⚠ — перед таблицами.
- Подразделы матрицы группируют разделы требований (обычно 3–4 подраздела).
- Столбец «Требования» — номера и диапазоны (`5.2.1–5.2.3`); группируй соседние пункты с одной реализацией и проверкой.
- Столбец «Реализация» — `ФАЙЛ: функция/сущность`; для кода вне модуля — описание («CAN-слой, вне модуля»).
- Столбец «Проверка» — тест-кейсы и/или буквы методов A/T/I/D.
- Каждый нормативный пункт должен встречаться в матрице. Каждый тест-кейс должен быть привязан хотя бы к одному требованию.
- Матрица для документа, написанного до реализации, заполняет «Реализация» планируемыми сущностями или «—».

## 14. Допущения и открытые вопросы

```markdown
### 13.1. Допущения

13.1.1. Страница эмулируемой EEPROM принадлежит подсистеме целиком (п. 6.1.4); иных потребителей нет.

### 13.2. Вопросы и решения

| № | Вопрос | Статус | Решение / комментарий | Пункты |
| :---: | :--- | :---: | :--- | :--- |
| 13.2.1 | Адрес и размер страницы, другие потребители | Закрыт | `0x0807F800`, 2048 байт, вся страница принадлежит реестру | 8.1.4–8.1.6 |
| 13.2.22 | Условие пустого FIFO | Открыт | Проверить на оборудовании | 5.6.13, TC-78 |

### 13.3. Примечания на будущее (информативно)
```

Правила:

- Допущение — утверждение, принятое без доказательства, на котором стоят требования. Каждое допущение ссылается на зависящие от него пункты.
- Вопрос формулируется так, чтобы на него можно было ответить коротко и однозначно; если ответ зависит от варианта, варианты перечисляются.
- Статусы: **Открыт**, **Закрыт**, **Отложен** (решено вернуться позже; указать условие возврата).
- Столбец «Пункты» — где решение записано нормативно (или какие пункты зависят от открытого вопроса).
- Вопросы не удаляются и не перенумеровываются. Новые вопросы получают следующий номер.
- Для открытых вопросов в тексте требований ставь ссылку на вопрос («см. 13.2.22») — это показывает читателю, что пункт может измениться.
- «Примечания на будущее» — идеи и темы вне текущей ревизии, чтобы они не терялись.

## 15. Приложения

Приложения обозначаются буквами; информативные помечаются в заголовке. Набор зависит от модуля; типовые:

| Приложение | Назначение | Когда нужно |
| :--- | :--- | :--- |
| Справочник сущностей (параметров, регистров, сообщений) | Таблица всех известных элементов с атрибутами и ссылками на пункты | Если есть перечень элементов |
| Сводка констант | Таблица `Константа | Значение | Пункт` — все числа документа | Всегда |
| Раскладка (памяти, кадра, страницы) | ASCII-схема в блоке кода | Если есть бинарный формат |
| Соглашение о ссылках на ТЗ из кода | Форма комментариев `// ТЗ 5.3.10`, `// TC-22: ТЗ 3.3.3`, пример, правило при исключении пункта | Всегда |
| Данные, восстановленные из журналов/кода | Таблица `Источник | Вывод | Пункты` | При обратной разработке |
| Расхождения с кодом и необходимые доработки | Таблица `Пункты ТЗ | Что требуется | Состояние | Доработка` | Если есть код, отличающийся от ТЗ |
| Пример реализации (информативно) | Эталонный код алгоритма, конфигурации | Для неочевидных алгоритмов |
| Обоснования и разборы | Анализ, на котором основано решение (таблица + вывод) | Если решение неочевидно |
| Контракт с внешним приложением (информативно) | Принципы, разбор клиентов, следствия для прошивки, рекомендации | Если есть внешние клиенты |

### Соглашение о ссылках из кода (обязательное приложение)

```markdown
## Приложение D. Соглашение о ссылках на ТЗ из кода

D.1. Ссылка на требование оформляется однострочным комментарием рядом с реализацией: `// ТЗ 5.3.10`. Для нескольких требований — перечисление через запятую: `// ТЗ 7.2.2, 7.2.3`.

D.2. Для тестов используется идентификатор тест-кейса и номера проверяемых требований: `// TC-22: ТЗ 3.3.3, 5.3.10`.

D.3. Пример:
    (блок кода)

D.4. При исключении требования его номер сохраняется с пометкой «(исключено)»; комментарий в коде удаляется вместе с реализацией.
```

### Расхождения с кодом

Каждая строка: какие пункты, что требуется, что сейчас в коде (конкретно: функция, тип, поведение), что нужно доработать. Внесённое в план или код отмечается «Внесено», несущественное — «Не требуется». Пункты с расхождениями помечаются ⚠ в матрице.
