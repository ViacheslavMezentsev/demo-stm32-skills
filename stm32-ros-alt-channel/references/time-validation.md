# Проверка времени Windows, WSL и платы

## Что установлено исследованием 19

Основание: предоставленный владельцем архив `19-wsl-stalls.zip`, README §14 (18.10.2026).
Ранний вывод §13.7 «ВМ останавливается, monotonic прячет паузу» **опровергнут самим исследованием**.
В том опыте `systemd-timesyncd` Ubuntu, chronyd системной ВМ WSL и Docker initd корректировали
общие часы ядра по разным опорам. Tick был 9152–9224 вместо около 10000; отношение
MONOTONIC/RAW — 0,9224. Realtime прыгал, а monotonic шёл медленнее, хотя ВМ продолжала исполняться.
После отключения конфликтующего timesyncd при работающем Docker: 240 с без скачков,
mono/host = 1,00006. Повторное включение воспроизвело проблему.
Это результат конкретного стенда, а не диагноз любой паузы WSL.

[Документация Ubuntu](https://ubuntu.com/wsl/docs/stable/explanation/time-sync/) подтверждает возможность
конфликта NTP гостя с синхронизацией Hyper-V. Ubuntu 24.04 и старше используют timesyncd;
в 25.10+ поведение chrony другое: нельзя механически применять старый рецепт ко всем версиям.
Не выполняйте скрипты исправления из архива автоматически. Сначала измерьте часы; не меняйте NTP,
службы, задания Windows и не делайте `wsl --shutdown` во время записи.

## Три независимые проверки

1. **UTC Windows**: `w32tm /query /status` и `w32tm /stripchart /computer:time.windows.com /samples:5 /dataonly`.
   Это смещение календарных часов, не проверка скорости счётчика платы.
2. **WSL относительно Windows**: UDP-опора `time.perf_counter()` Windows, а в WSL одновременно
   REALTIME, MONOTONIC и MONOTONIC_RAW. Длительность опыта — минимум 120 с (несколько прежних периодов 30 с).
3. **Плата относительно Windows**: чтения её счётчика через OpenOCD на Windows без halt/reset;
   отметки до/после чтения через `perf_counter`, середина интервала — оценка времени чтения,
   длительность чтения — неопределённость. Не считать nominal tick эталоном до этой проверки.

Из корня навыка, первое окно PowerShell (остановить Ctrl+C после опыта):

```powershell
python .\scripts\host_clock.py
```

Второе окно, заменив путь к скопированному навыку на свой путь WSL:

```powershell
wsl -d Ubuntu-20.04 -- python3 /mnt/d/project/skill/scripts/wsl_tick.py
wsl -d Ubuntu-20.04 -- systemctl is-active systemd-timesyncd
wsl -d Ubuntu-20.04 -- python3 /mnt/d/project/skill/scripts/host_ref_probe.py --seconds 120 --out /mnt/d/project/clock-report.json
```

Скрипты только читают часы; root не нужен. `inactive` может возвращать ненулевой код.
UDP 50123 должен быть свободен и доступен по loopback через mirrored networking.
`wsl_tick.py` использует полную структуру Linux x86-64 `timex`, включая хвостовые поля;
усечённую структуру передавать libc нельзя. Tick около 10000 — ожидание исследованного ядра,
а не универсальное доказательство правильности времени. Учитывайте также `freq_ppm` и внешний замер.

В JSON смотрите `ratios_to_host` (ожидаются близкие к 1), `realtime_steps` (скачки >20 мс относительно
monotonic), `max_rtt_raw_seconds`, параметры timex до/после. Большой RTT портит точность сравнения.
Близость к 1 оценивайте относительно требуемой точности и RTT, а не как точное равенство.
RAW служит дополнительной опорой, но тоже сверяется с Windows. Отсутствие скачков не исключает
плавного ухода частоты. Положительное постоянное смещение UTC не создаёт ошибки длительности.

## F411CE после выделения общей базы, 19.10.2026

Исходная версия: `d003ca5`. Прошивка stm32-hwtest-blackpill, HSI16 без PLL, SysTick LOAD=15999.
ROS MCAP: по 100 сообщений в семи топиках, 700 всего; `/bp/fault` всегда 0.
Между первым и последним `/bp/tick_ms`: 9,899757624 с меток ROS и 9,623 с счётчика MCU;
отношение 0,972044, разница около 2,80%. Интервалы tick 94–101 мс, повторов и обратного хода нет.
VDDA 3286–3291 мВ, температура 27,238–28,065 °C. Владелец подтвердил мигание LED после остановки.

Независимое чтение RAM с Windows (без ROS/WSL в тракте чтения, без halt/reset):
за 20,0547933 с счётчик MCU прибавил 19509 мс, отношение **0,9727849** (отставание 2,72%).
RCC CFGR=0, SysTick LOAD=15999. Это локализует основную разницу на стороне счётчика платы
относительно Windows; возвращение прежнего конфликта WSL для объяснения этой разницы не требуется.
HSI и программный SysTick не являются калиброванным эталоном. Возможны отклонение тактирования,
пропуск обслуживаний SysTick и влияние исполнения/отладки; конкретный механизм пока не доказан.
Сравнение с TIM2 приведено ниже; внешнее измерение MCO ещё не выполнено.
Не компенсировать разницу подменой timestamp или коэффициентом 1,028 без такого измерения.

Аппаратная проверка публикации и записи относится к `d003ca5`; новая автоматическая проверка
частоты тестируется отдельно с настоящим ROS и TCP-имитатором. UART/rosserial этим опытом не проверен.

Одновременно проверены часы WSL/Windows за 120 с: realtime/host=1,000033,
mono/host=1,000111, raw/host=1,000002, скачков realtime >20 мс нет, максимальный RTT 3,785 мс.
Tick ядра 10001, freq 4,63→9,60 ppm. Это отдельный текущий опыт, не измерение задним числом
во время ROS-записи. Он не воспроизводит прежний сбой WSL и вместе с прямым чтением MCU
не подтверждает WSL как источник основной ошибки 2,8%.

Контроль аппаратным TIM2 без перепрограммирования: PSC=15999, ARR=99; отсчёт составлен из
`app_state.timer_events * 100 + TIM2_CNT`, чтения через переполнение отбрасывались.
За 20,120543 с Windows: SysTick/Windows=0,972240, TIM2/Windows=0,972190.
Совпадение независимого периферийного таймера с SysTick делает объяснение только пропусками
SysTick недостаточным. Оба зависят от HSI; результат согласуется с общей скоростью тактирования
примерно 15,555 МГц вместо номинальных 16 МГц. Это **косвенная оценка**, не измерение HSI на выводе.
Прошивка и настройки тактирования не менялись; для окончательного вывода нужен MCO/частотомер.

В текущем Ubuntu-20.04 timesyncd — inactive/disabled. Настройки синхронизации в ходе проверки не менялись.
