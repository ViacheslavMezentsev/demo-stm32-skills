# Архитектура прошивок: STM32 + Arduino Core + CMake

Этот навык описывает архитектурный шаблон (scaffold) для создания промышленных прототипов на базе микроконтроллеров STM32. Шаблон берет лучшее от двух миров: богатую экосистему драйверов Arduino Core и строгие стандарты C++17 для встраиваемых систем (отсутствие кучи, строгая типизация, изоляция слоев).

## 🧠 Ключевые парадигмы

### 1. Архитектура «Синхронный Супер-цикл» (Synchronous Super-loop)
Программа строится вокруг одного бесконечного цикла, разделенного на две фазы:
- **Асинхронная фаза:** Выполняется в каждом такте `loop()`. Сюда входит сброс Watchdog, опрос буферов UART, обслуживание сетевых протоколов.
- **Синхронная фаза (Бизнес-логика):** Выполняется строго по таймеру (например, каждые 1 мс). Включает в себя опрос "железа" → вычисление математики → обновление конечного автомата (FSM) → применение состояний к выходам.

### 2. Отказоустойчивость (Fault Tolerance)
Запрещено использовать аппаратные зависания (`while(1)`) или вызовы `HardFault_Handler` при ожидаемых сбоях (например, просадка питания VDD, потеря датчика). Система должна переходить в программное состояние `HARDWARE_FAULT`, аппаратно блокировать опасные выходы, но **сохранять работу интерфейсов связи и терминала** для диагностики.

### 3. In-flight Parameter Lock (Блокировка конфигурации)
Если устройство (ПЛК, контроллер БПЛА) перешло в активный рабочий режим (например, `MOTOR_RUNNING`), любые входящие запросы на изменение параметров в RAM, стирание или сохранение в EEPROM **должны блокироваться**. Настройки меняются только в безопасном (пассивном) режиме.

### 4. Практическое моделирование ситуации (Role-Play)
Код должен отражать реальный физический мир. Если на плате есть мультиплексор, пины, реле и датчик, в коде должны быть классы `MuxManager`, `RelayDriver` и `SensorManager`. Конечный автомат (`FsmManager`) выступает "директором", который опрашивает менеджеров и раздает им команды.

## 🏗 Разделение кода (BSP и Бизнес-логика)

Файл `main.cpp` должен читаться как оглавление книги. В нем **категорически запрещено** использовать вызовы `HAL_*`, писать обработчики прерываний или напрямую работать с регистрами.

Вся "грязная" работа скрывается в модуле **BSP (Board Support Package)**.
* **Что в BSP:** `SystemClock_Config()`, `HardFault_Handler()`, низкоуровневая инициализация (I2C, ADC), поддержка эмулятора QEMU (Semihosting) и системный логгер.
* **Что в `main.cpp`:** Инстанцирование глобальных объектов, `setup()` с высокоуровневыми вызовами `.init()` и `loop()`.

## 💾 Управление памятью (Hard Real-Time)

В проекте **запрещено** использование динамической памяти (`new`, `malloc`, `std::vector`, `std::string`). Это исключает фрагментацию кучи и гарантирует аптайм.

**Использование `etl::optional<T>`:**
Часто сложные объекты требуют передачи зависимостей при создании, но глобальные объекты инициализируются до вызова `setup()`, когда аппаратная часть еще не готова (Static Initialization Order Fiasco).
* **Решение:** Объявляем глобальную переменную как `etl::optional<MyClass> obj;`. Объект не создается. В `setup()` вызываем `obj.emplace(arg1, arg2);`. Объект создается "на месте" (in-place) в статической памяти `.bss`. Никакой кучи!

**Использование Placement New для Фабрик:**
Если нужен полиморфизм (интерфейсы), выделяем статический буфер `alignas(8) uint8_t mem[128];` и конструируем нужный класс прямо в нем: `activeDriver = new (mem) SpecificDriver();`.

## 🔧 Структура вымышленного проекта (Простой ПЛК)

Представим прошивку ПЛК, который опрашивает датчик давления и управляет насосом.

* `Config.h` — Единый источник правды. Пины, baudrate, таймауты.
* `Bsp.h / Bsp.cpp` — Тактирование, логгер, обработка `HardFault`.
* `SensorManager` — Класс опроса АЦП / I2C датчика давления.
* `PumpDriver` — Класс управления MOSFET или реле насоса.
* `FsmManager` — Конечный автомат (Состояния: `IDLE`, `PUMPING`, `OVERPRESSURE_FAULT`).
* `main.cpp` — Инициализация и Супер-цикл 1 мс.

## 🛠 Подключение Arduino Core к CMake

Сборка осуществляется не через Arduino IDE, а через кастомный `CMakeLists.txt`. Arduino Core (исходники HAL, CMSIS, wiring) подключается как библиотека `INTERFACE`. 
Обязательно:
- Использование тулчейна `arm-none-eabi-gcc`.
- Флаг `-flto=auto` для удаления неиспользуемого кода HAL (освобождает до 20 КБ Flash).
- Замена `%f`/`%g` на целочисленную математику для исключения библиотеки `_printf_float` (экономит ~10 КБ Flash).
